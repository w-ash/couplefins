# v1.8.2 — Chat Write Parity

Status: Completed (2026-07-10)
Effort: L
Depends on: v1.8.1 (read tools — several mutations reference IDs surfaced by them)
Series overview: [v1.8.x — Agentic Chat](v1.8.x-agentic-chat.md)

## Goal

Every mutation a human can perform through the app becomes a chat tool, all
using the existing two-phase propose/confirm pattern. After this version,
`PENDING_PARITY_USE_CASES` in `src/application/chat/registry.py` is empty and
can be deleted (update the parity test accordingly).

## Context for a fresh agent

- **The two-phase pattern is non-negotiable** (prompt-injection defense: a
  mutation is a proposal until the human clicks Confirm). Flow:
  1. Propose handler in `src/application/chat/tool_executor.py`: validate
     (finalization check via `_check_finalization` for period-scoped writes,
     entity-exists checks, name→ID resolution), then `_propose_action(...)` →
     returns `{"status": "pending_confirmation", action_id, description, details}`.
  2. The frontend renders a ConfirmationCard; the user's next POST carries
     `confirmation: {action_id, approved}`.
  3. Executor in `src/application/chat/confirmed_actions.py` with signature
     `(action: PendingAction, current_user: Person) -> dict[str, object]`:
     atomic UoW, TOCTOU re-checks (re-verify the entity still exists /
     period still unlocked), single commit.
  4. Wire both into a `ToolSpec(kind="write", executor=..., broadcast_entity=...)`
     in `registry.py`. Broadcast entities must be valid `BroadcastEntity`
     literals (`src/infrastructure/events/event_bus.py`): settlements,
     transactions, uploads, reconciliation, budgets.
- Follow `update_budget` (propose: `handle_update_budget`; execute:
  `exec_budget`) end-to-end as the template.
- Descriptions lead with a trigger sentence AND state that the tool proposes
  (never applies) the change. Schemas set `strict: true` (house convention as
  of v1.8.1).
- **Confirmation cards must render concrete before/after details, never just
  an action name.** Anthropic's containment write-up (May 2026) measured ~93%
  of permission prompts being rubber-stamped — the details payload is what
  makes human confirmation a real defense rather than approval theater. The
  propose handler owns building those details (current amounts being deleted,
  counts being copied, where categories move, etc. — the Notes column below).
- Write tools never get `allowed_callers` — mutations stay main-loop
  proposals only. The v1.8.3 code-execution sandbox may call read tools
  programmatically but must never be able to invoke a write, even as a
  proposal.
- The registry shape test enforces executor + broadcast_entity on every
  write ToolSpec.

## Implementation notes (as shipped, 2026-07-10)

Deviations from the plan above, recorded for the next agent:

- **`strict: true` abandoned series-wide.** The "Schemas set strict: true"
  convention below is superseded — live API limits (20-strict-tool cap and
  a compiled-grammar size cap at this registry's 31 tools) forced dropping
  strict from every schema. Handler validation is the boundary;
  `test_no_strict_schemas` pins it. See the series overview conventions and
  the learnings section in v1.8.3.
- `record_settlement` also accepts optional `linked_transaction_ids`
  (candidate IDs from get_settlement_activity) — the UI records with links,
  so capability parity required it.
- `copy_budgets` has no `scope` param: `CopyBudgetsUseCase` copies household
  plus the current user's personal budgets in one operation.
- `set_category_personal` rejects no-op proposals (flag already at the
  requested value) with an actionable error instead of proposing nothing.
- `update_transaction_split` proposals always carry a `splits` list in
  details (the executor reads only that); single-entry proposals ALSO
  flatten the first row's keys so the bespoke SplitDetails card keeps
  rendering. Batch proposals render through the generic card.
- Tool naming now carries read/write semantics: reads are `get_*`/`search_*`,
  writes anything else. The frontend derives its "Proposing vs Looking up"
  indicator from this (`isMutationTool`), and
  `test_read_write_naming_convention` enforces it. v1.8.3's
  `delegate_analysis` must extend this convention (see its learnings).
- Category-setup writes broadcast `"reconciliation"` (no dedicated
  categories entity); budget writes broadcast `"budgets"`, settlement
  writes `"settlements"`, finalize/unfinalize `"reconciliation"` — matching
  the REST routes where they exist.

## Registry bookkeeping

- Move each use case from `PENDING_PARITY_USE_CASES` into its ToolSpec's
  `use_cases`. When the set is empty, delete it and drop it from the parity
  test's classification union.
- `UpdateBudgetUseCase` (PUT /budgets/{id}) is covered by the existing
  `update_budget` tool's upsert semantics via `SaveBudgetUseCase` — add
  `"UpdateBudgetUseCase"` to that ToolSpec's `use_cases` tuple rather than
  building a separate tool (capability parity, not endpoint parity).
