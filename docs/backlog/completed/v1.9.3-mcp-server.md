# v1.9.3 — MCP Server over the Tool Registry

Status: Completed (2026-07-16)
Effort: M-L
Depends on: v1.9.0 (registry restructure); independent of v1.9.1/v1.9.2
Series overview: [v1.9.x — Context Engineering](v1.9.x-context-engineering.md)

## Goal

Expose the chat tool registry to external agents (Claude Code, other MCP
clients) over stdio — same tools, same two-phase write confirmation, one
registry. Crib mixd `src/interface/mcp/` nearly wholesale (its docstrings
carry the SDK verification notes).

Read + write tools are exposed; **agentic tools stay chat-only** (the MCP
client brings its own loop/sandbox). Writes use in-band two-phase
confirmation: a call without `confirm=true` returns
`{status: "needs_confirmation", confirm_token, description, preview}`; a
second call with the token and unchanged arguments commits. This reuses the
chat's `pending_action_store` and confirmed-action executors — no duplicate
store, one preview renderer, two surfaces.

## Tasks

- [x] **`src/interface/mcp/exposure.py`** — single SDK-free classifier
  `mcp_exposure(spec)` from `spec.kind` (read/write → exposed, agentic →
  chat-only), shared by the server and tests so they can't drift.
- [x] **`src/interface/mcp/server.py`** — low-level `mcp` SDK server:
  `tools/list` from REGISTRY (annotations derived from kind: reads
  read-only+idempotent, writes destructive, closed world; write schemas
  augmented with `confirm`/`confirm_token` properties), `tools/call`
  dispatching to `execute_tool` / `handle_write_call`; `ToolExecutionError`
  → `is_error` tool result (model self-corrects), not a protocol error;
  strip `<user_data>` tags from results (an MCP client is untaught — the
  tags are noise there, not defense).
- [x] **`src/interface/mcp/confirmation.py`** — `handle_write_call`:
  preview path validates the dispatcher returned a proposal; confirm path
  claims the token (owner-checked, 5-min TTL), **rejects on args drift**
  (stripped confirm-time args must equal stored `tool_input`), re-previews
  cleanly on expired/malformed tokens. Note: mixd's store `claim` is async;
  couplefins' is sync — adapt the call.
- [x] **Identity** — env var (e.g. `COUPLEFINS_MCP_PERSON`) names the acting
  person; resolve to a `Person` via `list_persons` (couplefins'
  `ToolContext` carries `current_user: Person` + `persons`, not a bare id).
  Fail fast with an actionable error when unset/unknown.
- [x] **Entrypoint + install** — `python -m src.interface.mcp` (or a
  `[project.scripts]` console script); stdout is JSON-RPC so logging must go
  to stderr (verify structlog config); `install.py` writes the client
  config entry (`claude mcp add` compatible).
- [x] **Dependency** — add the `mcp` SDK (mixd pins `mcp==2.0.0b1` /
  `mcp-types==2.0.0b1` with a re-verify note for the 2026-07-28 stable v2;
  check what's current at implementation time).
- [x] **Tests** — crib mixd `tests/unit/interface/mcp/`: exposure
  classification completeness (every REGISTRY spec classified), annotations
  from kind, confirm-token round-trip, args-drift rejection, expired-token
  re-preview, stdout purity. Parity suite gains the exposure check.

## Accepted limitations (document, don't build around)

- **SSE invalidation gap**: the MCP server is a separate process from the
  web app; confirmed writes can't broadcast on the in-memory `EventBus`.
  The 5-second polling fallback on together-session pages covers it.
- **`pending_action_store` is per-process** — fine: preview and confirm both
  happen inside the MCP server process.
- Long-running operations: couplefins has none (no `launches_operation`
  concept) — the mixd gating logic drops out.

## Acceptance

- From Claude Code (`claude mcp add`): tools list shows reads/writes with
  correct annotations; a read returns data; a write previews then commits
  on confirm; mutating an argument between preview and confirm is rejected;
  an expired token re-previews.
- Full quality gate green.

## Implementation learnings (2026-07-16)

- Pinned `mcp==2.0.0b1` / `mcp-types==2.0.0b1` (same live-verified pin as
  mixd). RE-VERIFY on the 2026-07-28 stable-v2 bump before extending the
  server.
- Live-verified over real stdio (SDK client → `python -m src.interface.mcp`
  subprocess → Neon): 31 tools listed, real read, write preview with
  human-readable description, args-drift rejection, consumed-token
  re-preview. Propose-only — no live commit was made; the commit path is
  the same `execute_confirmed_action` the chat confirms through.
- couplefins' `ToolContext` requires an LLM client; the server binds a
  `_UnavailableLLM` stand-in that raises — no MCP-exposed tool touches it.
- `setup_stderr_logging()` added to `src/config/logging.py`: the app's
  console handler targets stdout, which would corrupt JSON-RPC.
