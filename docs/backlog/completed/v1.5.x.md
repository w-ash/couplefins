The patterns are battle-tested — what changes is the domain (books → household finance) and the LLM interaction mode (RAG retrieval → tool use).

### What's new (not in Mimir)

| Component | Why |
|---|---|
| Tool definitions + tool executor | Mimir uses RAG. We use Claude's tool-use API to call existing use cases. |
| Agentic while-loop with tool round-tripping | Backend loops: call Claude → get `tool_use` → execute tool → feed `tool_result` back → repeat until `end_turn`. Mimir's LLM call is single-shot. |

## Design Decisions

**The chat assistant is a shortcut, not a replacement.** Every action the assistant can perform is already available through the existing UI. The assistant makes it faster to ask questions and perform routine edits — it doesn't unlock new capabilities. If the assistant is unavailable (no API key configured, quota exhausted), the app works identically.

**Assistive, not controlling.** The assistant lives in the periphery — present, optional, and respectful of the primary workflow. It augments context, it doesn't hijack the flow. Outputs are informational, not authoritative — the user decides what to do with the answer.

**Right-edge panel, not a floating widget.** The chat panel is part of the app layout, not a support-chatbot bubble floating over content. A small icon tab on the right edge of the viewport opens a ~400px panel. When open, the main content area compresses to make room (no overlay, no obscured content). This follows the pattern used by GitHub Copilot, Cursor, and Microsoft 365 Copilot for secondary assistants alongside complex primary tasks. The left sidebar's mental model is "navigate to a page" — adding a chat item that opens a panel would break that pattern.

**Suggested questions for discoverability.** An empty chat box is a dead end. On first open (no messages yet), the panel shows 3-4 tappable question chips relevant to the current state ("Who owes whom?", "Are we on budget?"). This surfaces capabilities without a tutorial.

**Desktop: content-compressing panel. Mobile: full-screen page.** On desktop (≥md), the panel slides in from the right and the content area shrinks. On mobile (<md), chat is a full-screen page accessible from the "More" menu (alongside Upload and Settings) with a back button to return. No bottom sheet — a full page is simpler and consistent with how other secondary features work on mobile.

**Read-first, write-later.** v1.5.0 ships read-only tools. Mutation tools (budget edits, transaction updates) arrive in v1.5.2 behind a confirmation step. This keeps the first version simple and risk-free.

**Backend-orchestrated agentic loop.** The Anthropic Python SDK runs the tool-calling loop server-side. The frontend is a simple SSE consumer — the same queue-bridge pattern from Mimir. The frontend never talks to the Claude API directly.

**Conversations are ephemeral.** No persistence in v1.5.x. The chat panel starts fresh on page refresh. The couple asks quick questions during solo prep or the together session — they don't need searchable chat history. If usage patterns demand it, we port Mimir's conversation persistence later.

**Tools map to existing use cases.** Each chat tool is a thin wrapper around an existing use case. No new data access paths, no raw SQL. The assistant can only do what the API already does.

**Mutations require explicit confirmation.** The model proposes changes via a structured `pending_confirmation` event. The frontend renders a confirmation card. The user clicks Confirm or Cancel. The model never auto-executes writes.

**Context-aware system prompt.** Includes the current user's name, partner's name, current date, and category group list. Lets the model answer simple contextual questions with a single tool call instead of multiple lookups. No user-generated content in the system prompt — merchant names and notes flow through tool results only.

**Scoped to the authenticated user.** The chat endpoint uses the same `get_current_user` JWT dependency. Tool calls execute with the authenticated user's person_id. Alice can't modify Bob's personal budgets via chat.

**Graceful degradation.** No `ANTHROPIC_API_KEY` → icon tab hidden, mobile route not registered. API error mid-stream → error event rendered inline, user can retry. Rest of the app is unaffected.

**Model: Claude Sonnet 4.6.** Near-Opus performance at 1/5 the cost ($3/MTok input, $15/MTok output vs Opus at $5/$25). Benchmarks show Sonnet 4.6 within ~1 point of Opus 4.6 on tool use and computer use tasks. Haiku 4.5 is cheaper but less reliable for multi-tool routing — not worth the risk in a data app. Use the stable model ID (e.g., `claude-sonnet-4-6`), not a dated snapshot, so we track improvements automatically. Model is a single constant in `ChatConfig` — easy to swap.

**Prompt caching from day one.** The system prompt + tool definitions are identical on every chat turn. With Sonnet 4.6's 2,048-token minimum and our expected ~3-5K tokens of prompt + tools, every request after the first will hit cache. Cache reads cost 10% of base input tokens — a ~90% cost reduction on the static prefix. We mark `cache_control: {"type": "ephemeral"}` on the last tool definition (caches all tools) and the last system prompt block (caches system + tools together). Default 5-minute TTL is correct — the couple typically asks several questions in quick succession during the together session.

### v1.5.0: Chat Assistant — Read-Only Queries
**Goal**: A chat panel where either partner can ask natural-language questions about their spending, budgets, and settlement status. Read-only — no mutations.
**Status**: Completed (2026-04-10)
**Context**: The couple's primary questions — "Who owes whom?", "Are we over budget on dining?", "What did we spend at Whole Foods?" — currently require navigating to the right page, selecting the right month, and reading the right section. A chat interface answers these directly. Fulfills the unscheduled "natural language spending queries" item.
**What this unlocks**: Instant answers to spending questions during solo prep or the together session. A faster path to "do I need to dig deeper?" without page-hopping.

#### User stories

**US-CHAT-1**: As a partner, I want to ask spending questions in plain language and get answers from our data.

- Given the chat panel is open, when I type "How much did we spend on dining in March?", then the assistant queries our transaction data and responds with the total, broken down by category if relevant
- Given I ask "Who owes whom for March?", then the assistant returns the settlement balance for that month
- Given I ask a question about a month with no data, then the assistant tells me no transactions exist for that period
- Given I ask an ambiguous question ("How's the budget?"), then the assistant asks a clarifying follow-up or assumes the current month and states its assumption

**US-CHAT-2**: As a partner, I want the chat panel accessible from any page without losing my place.

- Given any page in the app on desktop, then I see a small icon tab on the right edge of the viewport
- Given I click the icon tab (or press ⌘K), then a chat panel expands from the right and the page content compresses to make room
- Given the panel is open, then I can still interact with the page content (scrolling, clicking links) — the content is narrower but fully functional
- Given I close the panel (click close button, press Escape, or press ⌘K again), then the content expands back and my conversation is preserved until I navigate away or refresh
- Given the API key is not configured, then the icon tab does not render

**US-CHAT-3**: As a partner, I want the assistant to know who I am and what month it is without me having to say so.

- Given I'm logged in as Alice and ask "What do I owe?", then the assistant checks settlement for the current active month from Alice's perspective
- Given I ask "Are we over budget?", then the assistant checks household budgets for the current month
- Given I ask about "last month", then the assistant resolves it relative to the current date

**US-CHAT-4**: As a partner, I want to see the assistant's progress when it's looking things up.

- Given the assistant needs to query data, then I see a brief indicator ("Looking up March spending...")
- Given the response is streaming, then I see text appear progressively (not all at once after a delay)
- Given a tool call fails, then I see a clear error message and can retry my question

**US-CHAT-6**: As a partner on mobile, I want to ask questions without the chat blocking the whole app.

- Given I'm on a mobile viewport, then the "More" menu includes an "Ask" item (alongside Upload and Settings)
- Given I tap "Ask", then I navigate to a full-screen chat page with a back button
- Given I'm in the chat page, then the experience is identical to the desktop panel — same messages, same streaming, same tool indicators
- Given I press back, then I return to the page I was on (conversation is lost on navigation, same as desktop)

**US-CHAT-7**: As a partner, I want to see example questions so I know what to ask.

- Given I open the chat panel (or page) with no prior messages, then I see 3-4 suggested questions as tappable chips
- Given the suggestions are context-aware: if there's an outstanding balance, one chip is "Who owes whom?"; if budgets are set, one is "Are we on budget?"
- Given I tap a suggestion, then it populates the input and sends immediately

#### Backend

- [x] **SSE streaming module (port from Mimir)**
    - Effort: S
    - What: Port `stream_ask_response()` queue-bridge pattern from Mimir's `src/interface/api/sse.py`. Discriminated `asyncio.Queue[str | _ToolEvent | _StepEvent | None]` — strings are text deltas, `_ToolEvent` carries tool call metadata, `_StepEvent` marks phases, `None` is the completion sentinel. `None` sent on both success and error paths. `X-Accel-Buffering: no` header. Adapt Mimir's `AskDoneEvent` to a simpler `ChatDoneEvent` (no token usage, no passages, no compaction).
    - Port from: `mimir/src/interface/api/sse.py`

- [x] **Chat endpoint**
    - Effort: M
    - What: `POST /api/v1/chat` accepts `{messages: [{role, content}]}`, authenticates via `get_current_user`. Uses a module-level `anthropic.AsyncAnthropic` client (created at app startup, reused per request). Wraps the loop in the Mimir queue-bridge pattern — `asyncio.create_task(run_chat())` as the background task, `event_generator()` reads from queue and yields SSE lines.
        **Streaming API pattern** (from [Python SDK helpers](https://github.com/anthropics/anthropic-sdk-python/blob/main/helpers.md)):
        ```python
        async with client.messages.stream(
            model="claude-sonnet-4-6",
            max_tokens=4096,
            system=SYSTEM_PROMPT,  # list of blocks with cache_control on last
            tools=TOOLS,  # list with cache_control on last tool
            messages=messages,
        ) as stream:
            async for event in stream:
                if event.type == "text":
                    queue.put_nowait(event.text)  # stream to SSE
                elif event.type == "content_block_stop":
                    block = event.content_block
                    if block.type == "tool_use":
                        queue.put_nowait(_ToolEvent(name=block.name))  # "Looking up..."
            final = await stream.get_final_message()
        ```
        **Agentic loop** (Ring 3 pattern): after each `stream.get_final_message()`, check `final.stop_reason`. If `"tool_use"`, iterate all `tool_use` blocks in `final.content`, execute them via `tool_executor`, append `{"role": "assistant", "content": final.content}` and `{"role": "user", "content": [tool_result, ...]}` to messages, then stream the next turn. Loop until `stop_reason == "end_turn"`. Max 8 rounds.
        **Cancellation**: on `asyncio.CancelledError` (client disconnect), call `stream.close()` to abort the upstream Anthropic request.
        **Error mapping**: reuses existing `error_handling.py`. Add chat-specific codes: `CHAT_UNAVAILABLE` (no API key), `TOOL_EXECUTION_ERROR`, `MAX_ROUNDS_EXCEEDED`, `ANTHROPIC_API_ERROR`.
    - Port pattern from: `mimir/src/interface/api/routes/books.py` (the `/ask` endpoint structure)
    - Files: `src/interface/api/routes/chat.py` (new), `src/interface/api/schemas/chat.py` (new)

### v1.5.2: Chat Mutations with Confirmation
**Goal**: Let the assistant make changes — update budgets, edit transaction splits, tag transactions — with explicit user confirmation before each mutation. Ship domain boundary and tool result framing alongside mutations since the model can now execute writes.
**Status**: Completed (2026-04-10)
**Context**: Read-only chat is useful but limited. The most common follow-up to "Are we over budget on dining?" is "Lower it to $700." Requiring the user to navigate to the Budget page for a one-field edit breaks the conversational flow.
**What this unlocks**: End-to-end conversational workflows. Ask a question, get an answer, make an adjustment — all without leaving the chat panel.

#### User stories

**US-CHAT-8**: As a partner, I want to update budgets through the chat with a confirmation step.

- Given I say "Set the Food & Dining budget to $700 for April", then the assistant shows a confirmation card: "Set Food & Dining to $700.00 for April 2026? [Confirm] [Cancel]"
- Given I click Confirm, then the budget is updated and the assistant confirms the change
- Given I click Cancel, then nothing changes and the assistant acknowledges the cancellation
- Given the month is finalized, then the assistant tells me the month is locked and I need to unfinalize first

**US-CHAT-9**: As a partner, I want to edit transaction splits through the chat with a confirmation step.

- Given I say "Change the Whole Foods transaction from March 15 to 70/30", then the assistant finds the matching transaction and shows a confirmation card with transaction details and the proposed split change
- Given multiple transactions match, then the assistant lists them and asks me to clarify which one
- Given I confirm, then the split is updated and the audit trail records the change

**US-CHAT-10**: As a partner, I want to tag transactions through the chat.

- Given I say "Tag all the Uber Eats transactions from March as household", then the assistant shows a confirmation card listing the affected transactions and the proposed change
- Given I confirm, then the transactions are updated (household flag set, audit trail recorded)
- Given the count is large (>10), then the assistant confirms the count before showing the full confirmation
