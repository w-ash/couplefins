# v1.4.x: Transaction Edit History

For strategic overview, see the [planning overview](README.md).

## Scope Design Decisions

**Import provenance is derived from the upload, not stored as a TransactionEdit.** Each transaction has `upload_id` FK pointing to `Upload(person_id, uploaded_at)`. The edit history endpoint fetches the upload and returns it as an `import_event` alongside the edit list. This avoids creating synthetic "imported" TransactionEdit records for every transaction, avoids a retroactive backfill, and keeps the edit table focused on actual field changes.

**Person attribution is nullable.** `edited_by_person_id: UUID | None` on TransactionEdit. Historical edits (pre-v1.4.0) get `None` — no backfill. The UI gracefully omits the person name when null.

**Person names are resolved client-side.** The `TransactionsPage` already has a `personNames` Map via `usePersonMaps()`. The API returns `edited_by_person_id` and the import event's `person_id` — the frontend looks up names locally. No server-side name resolution needed.

**`edited_by_person_id` is server-derived only.** The field is populated from the authenticated user's JWT (`current_user.id`) in route handlers and threaded through commands. It is never accepted from request bodies — it must not appear in `BulkUpdateRequest`, `UpdateTransactionRequest`, or any other client-facing request schema.

**Re-upload shows the most recent import date.** When a CSV is re-uploaded (same person + month), the old Upload is replaced and transactions are reassigned to the new `upload_id`. The `imported_at` in the timeline therefore reflects the latest re-upload, not the original import. This is correct behavior — the most recent upload is the authoritative source of the current data.

**The edit count indicator on collapsed rows is deferred.** Showing a pencil icon on edited transactions would require a subquery or join on every transaction list fetch. For a 2-person tool with rare edits, the cost outweighs the benefit. The timeline is visible when the row is expanded — that's sufficient.

### v1.4.0: Edit Attribution
**Goal**: Record who made each transaction edit so the history can show "Alice changed..." instead of just "changed..."
**Status**: Completed (2026-04-07)
**Context**: The existing TransactionEdit entity tracks what changed, when, and the old/new values — but not who made the change. The authenticated user is available via `Depends(get_current_user)` in every route handler but is never threaded into use case commands. In a 2-person household, knowing who made an edit matters during the together session.
**What this unlocks**: Person attribution on every new edit. Foundation for v1.4.1 (enriched API) and v1.4.2 (frontend timeline with names).

### v1.4.1: Import Provenance Endpoint
**Goal**: The edit history endpoint returns a complete lifecycle timeline — import event (derived from upload) plus edit events.
**Status**: Not started
**Context**: Today the endpoint returns raw `TransactionEdit` records. The frontend can't show "Imported by Alice on Mar 15" because the import event isn't in the edit table. With v1.4.0 providing `edited_by_person_id`, this version adds the import provenance by looking up the transaction's upload.
**What this unlocks**: The frontend can render a complete timeline from a single endpoint without additional API calls.

#### Backend

- [ ] **Domain value object: `ImportEvent`**
    - Effort: S
    - What: New frozen attrs value object `ImportEvent(person_id: UUID, imported_at: datetime)` in the domain layer alongside `TransactionEdit`. Same category of fact — it represents a lifecycle event on a transaction.
    - Files: `src/domain/entities/import_event.py` (new)

- [ ] **Use case: enrich `GetTransactionEditsUseCase` with import event**
    - Effort: M
    - What: The use case already fetches the transaction (for the 404 guard) — access `tx.upload_id` from that. Fetch the `Upload` entity via `uow.uploads.get_by_id(tx.upload_id)`. Construct `ImportEvent(person_id=upload.person_id, imported_at=upload.uploaded_at)`. Return a new result shape with `import_event: ImportEvent | None` alongside `edits`. `import_event` is `None` only if the upload was deleted (edge case). Note: `Upload.uploaded_at` must be UTC-aware — verify during implementation and add a defensive assertion if needed.
    - Files: `src/application/use_cases/get_transaction_edits.py`

- [ ] **API schema: `ImportEventResponse` + enriched `TransactionEditHistoryResponse`**
    - Effort: S
    - What: New `ImportEventResponse(person_id: UUID, imported_at: datetime)`. Add `import_event: ImportEventResponse | None` to `TransactionEditHistoryResponse`. Route handler maps from the enriched use case result.
    - Files: `src/interface/api/schemas/transactions.py`, `src/interface/api/routes/transactions.py`

### v1.4.2: Transaction History Timeline
**Goal**: Replace the plain edit list with a vertical timeline showing the full transaction lifecycle — import event as the anchor, subsequent edits with person names.
**Status**: Not started
**Context**: The current `EditHistory` component (in `TransactionEditor.tsx`) shows edits as plain `<p>` elements with no import context and no person attribution. 99% of transactions will show only the import event (no edits). The timeline should feel lightweight — a subtle left-border with small dots, not a heavy enterprise audit log.
**What this unlocks**: US-REVIEW-3 acceptance criteria fully met ("an audit trail records what changed, when, and the previous value"). Partners can see who made each change during the together session.
