# v0.10.x: Mobile, Consistency & Quality

For strategic overview, see the [planning overview](README.md).

**Research basis**: Before designing this version series, we audited every page and shared component for responsiveness and consistency, and reviewed 2026 mobile finance app patterns (bottom nav, card layouts, touch targets, progressive disclosure). Key findings:

- **The app has two ages of UI.** Pages shipped v0.7.0+ (Upload, Insights, Budget) have responsive grids, mobile/desktop content splits, and `sm:`/`md:` breakpoints. Pages shipped v0.2.0–v0.6.x (Dashboard, Transactions, Settle Up, Settings) assume desktop width — no breakpoints, `py-12` padding on mobile, tables that only scroll horizontally. The consistency gap between "good pages" and "old pages" is the main quality problem.
- **Settings is janky on desktop too.** `CategoryMappingEditor` crams four inline controls into a tight `flex` header row. The icon picker uses `absolute left-0 top-full` (overflows on mobile). Unmapped rows have a hardcoded `w-48` select. `PersonAccountSettings` has a `pt-6` button that assumes desktop width. This page needs a quality pass regardless of mobile.
- **Shared components have no mobile story.** `PageHeader` puts title and controls in `flex justify-between` — DateRangePicker overflows on narrow screens. `StatsGrid` jumps from `grid-cols-2` to `grid-cols-3` with no `grid-cols-1` for phones. `Card` is always `p-6` with no compact variant. All pages use `px-6 py-12` — `py-12` wastes 96px of vertical space on a 667px phone screen.
- **Two competing heading patterns.** Older sections use heading-only (`mb-4 font-medium text-lg`). Newer sections (v0.8.5 Insights) add a one-line description below the heading (`mb-1` heading + `mb-4 text-xs text-muted-foreground` description). The described pattern is better — it explains *why* a section is useful. Should be the standard everywhere.
- **Two competing chevron patterns.** Budget and CategoryMappingEditor use a single `ChevronDown` with `-rotate-90` CSS transform when collapsed (animated, one component). Transactions `CategoryGroupRow` conditionally renders `ChevronDown` vs `ChevronRight` (no animation, two components). The animated single-component pattern is canonical.
- **Form labels vary.** SettleUp and TransactionEditor use `text-sm font-medium text-foreground`. Budget's AddBudgetForm uses `text-xs font-medium text-muted-foreground`. Should be one pattern.
- **Bottom nav**: 5 items is the sweet spot for thumb-zone ergonomics (Apple HIG, Material Design 3). The app has 7 sidebar items. Solution: 5 primary tabs (Dashboard, Transactions, Settle Up, Budget, Insights) + a "More" tab that opens a bottom sheet with Upload, Settings, and the identity toggle. Standard pattern (Instagram, Spotify, most finance apps).
- **Card-per-row for tables on mobile**: The Upload page (v0.8.0) already implements this — `sm:hidden` card layout + `hidden sm:block` table. This is the internal prior art pattern for Transactions and Dashboard month history.
- **Touch targets**: WCAG 2.5.8 and Apple HIG specify 44px minimum. Current icon buttons (`p-1.5` + `size-4` icon = ~28px) and checkboxes (`size-4` = 16px) are well below. Number inputs lack `inputMode="decimal"` for the numeric keyboard.
- **Popovers break on mobile**: DateRangePicker, MonthPicker, IconPicker, and filter dropdowns are all absolutely-positioned popovers sized for desktop. On a 375px phone, they overflow or clip. Standard mobile pattern: convert popovers to bottom sheets or full-screen modals below `sm:`.
- **Anti-slop = consistency**: The app already has a distinctive design language — Satoshi font, warm OKLch palette, teal/coral semantics, no Inter, no gradients. The anti-slop move is making these choices *coherent* across every page, not just the recent ones. A warm, intentional Dashboard next to a default-feeling Settings page undermines the whole identity.

### v0.10.0: App Shell + Shared Component Foundations
**Goal**: Transform the app shell for mobile and fix the shared components every page depends on.
**Context**: The sidebar is a fixed `w-56` column that renders on every viewport. No mobile nav exists. Shared components (`PageHeader`, `StatsGrid`, page container padding) have no responsive behavior — they work on desktop by luck of `max-w-4xl` centering. Every page-level responsive fix in v0.10.1–v0.10.2 depends on the shell and shared components being mobile-ready first.
**What this unlocks**: The app renders and navigates correctly on a phone. Shared components adapt to viewport. Foundation for all page-level work.

#### App Shell

- [x] **Bottom navigation bar**
    - Effort: M
    - Dependencies: v0.9.3
    - What: Below `md:` breakpoint, replace the sidebar with a fixed bottom tab bar. Five primary tabs: Dashboard, Transactions, Settle Up, Budget, Insights — each with a Lucide icon + short label. Active tab highlighted with `text-primary` + subtle indicator. The tab bar sits in the thumb zone (bottom of screen). `AppLayout.tsx` conditionally renders sidebar (desktop) or bottom nav (mobile) using a `md:hidden` / `hidden md:flex` split. The sidebar component stays unchanged above `md:`.
    - Why: Bottom nav is the established mobile pattern for 3–5 primary destinations. Keeps the most-used pages one tap away.
    - Notes:
        - Tab bar height: ~56px (48px content + 8px safe area for notched phones via `pb-safe`)
        - Icons: reuse the same Lucide icons already in the sidebar
        - Active indicator: `border-t-2 border-primary` on the active tab, or a small dot — match the sidebar's active state semantics

- [x] **"More" sheet for overflow items**
    - Effort: S
    - Dependencies: "Bottom navigation bar"
    - What: The "More" tab (ellipsis icon + "More" label) opens a bottom sheet with: Upload, Settings, and the identity toggle (person switcher). The sheet slides up from the bottom with a backdrop. Tapping outside or swiping down dismisses it. Sheet items match the sidebar's navigation item styling. The identity toggle shows both person badges with the current person highlighted — same visual as the sidebar's bottom section.
    - Why: Upload and Settings are lower-frequency actions (used monthly in solo prep, not during quick phone checks). The identity toggle is rarely used but must remain accessible. Hiding them behind one tap keeps the primary nav clean.
    - Notes:
        - Sheet pattern: `position: fixed`, `bottom: 0`, `transform: translateY()` animation. Native `<dialog>` or a lightweight sheet component — not a full modal library.
        - The sheet should feel lightweight — no overlay dimming, just a subtle backdrop blur or `bg-black/20`.
        - On desktop, none of this renders. The sidebar handles everything.

#### Shared Components

- [x] **PageHeader responsive stacking**
    - Effort: S
    - Dependencies: none
    - What: Change `PageHeader.tsx` from `flex items-center justify-between` to `flex flex-col gap-3 sm:flex-row sm:items-center sm:justify-between`. On mobile, the title and controls (DateRangePicker, MonthPicker) stack vertically. On desktop, unchanged. This affects every page that passes `children` to PageHeader (Transactions, Settle Up, Budget).
    - Why: DateRangePicker in the Transactions header overflows on a 375px screen. Stacking is the simplest fix that works for all pages.

- [x] **StatsGrid mobile layout**
    - Effort: S
    - Dependencies: none
    - What: Change `StatsGrid.tsx` grid classes. Currently: `grid-cols-3` (for ≤3 stats) or `grid-cols-2 sm:grid-cols-4` (for 4+). New: `grid-cols-1 sm:grid-cols-3` (for ≤3) and `grid-cols-2 sm:grid-cols-4` (for 4+, already correct). The 3-stat case is the problem — `grid-cols-3` at 320px gives each stat ~93px, too narrow for labels like "Year-to-date balance."
    - Why: Stats are unreadable at phone widths with the current 3-column default.

- [x] **Page container mobile padding**
    - Effort: S
    - Dependencies: none
    - What: All seven pages use `px-6 py-12` (or similar). Change to `px-4 py-6 md:px-6 md:py-12`. This is a find-and-replace across page components. `px-4` gives 16px horizontal padding (standard mobile), `py-6` gives 24px vertical (adequate breathing room without wasting a phone screen's limited height).
    - Why: `py-12` is 96px of top+bottom padding — 14% of a 667px iPhone screen wasted on whitespace.
    - Notes: Settings already uses `max-w-3xl` (narrower); Upload uses `max-w-3xl md:max-w-5xl` (responsive). Preserve those per-page differences.

- [x] **Form input mobile foundations**
    - Effort: XS
    - Dependencies: none
    - What: In `web/src/lib/input-styles.ts`, add `min-h-11` (44px) to `baseInputClass` and `selectInputClass`. This ensures all inputs and selects meet the WCAG 2.5.8 touch target minimum. Also add `inputMode="decimal"` to all number `<input>` elements (PercentInput, settlement amount, budget amount) so mobile browsers show the numeric keyboard.
    - Why: Current inputs are ~36px tall (`py-2` + `text-sm`). The 8px gap between that and the 44px minimum causes real tap errors on phones. `inputMode` is a one-attribute change that transforms the mobile number entry experience.

**Context**: With the app shell and shared components responsive (v0.10.0), each page needs its own content adapted. The couple's primary mobile use case is quick checks: "who owes whom?", "are we on budget?", "what did we spend on?" Full editing (bulk edit, inline transaction editor) remains desktop-oriented — mobile optimizes for reading and light interaction.
**What this unlocks**: The couple can check settlement status, review recent transactions, and glance at budget health from their phones. Solo prep benefits too — you can review your upload results on the bus.

### v0.10.2: Settings Page Overhaul
**Goal**: Bring the Settings page to the quality bar of Upload and Insights — polished on desktop, fully functional on mobile.
**Context**: Settings is the jankiest page in the app. The `CategoryMappingEditor` crams icon picker + rename + delete buttons into a cramped horizontal row that's hard to use even on desktop. The icon picker is an absolutely-positioned grid that can overflow the viewport. Unmapped category rows have a hardcoded `w-48` select. `PersonAccountSettings` has awkward spacing. The page also lacks section descriptions (the pattern introduced in v0.8.5). This is a desktop+mobile quality pass — not just "make it responsive."
**What this unlocks**: A Settings page that matches the polish of the rest of the app. Category management that works on a phone. Consistent section heading pattern app-wide.

### v0.10.3: Interaction Consistency + Touch Polish
**Goal**: Cross-cutting audit to unify interaction patterns, ensure touch usability, and bring every page to the same quality bar.
**Context**: Each version series introduced its own micro-patterns — heading styles, chevron animations, form labels, popover behaviors. These small inconsistencies accumulate into a feeling of "different developers built different pages" — exactly the AI-slop aesthetic the couple wants to avoid. This version standardizes the patterns and completes the mobile experience with proper touch targets and popover-to-sheet conversions.
**What this unlocks**: A coherent, intentional experience where every expandable section, every heading, every form label, and every interactive element feels like the same hand built it.

#### Pattern Unification

- [ ] **Chevron expand/collapse standardization**
    - Effort: S
    - Dependencies: v0.10.2
    - What: Two competing patterns exist:
        - **Pattern A** (Budget, CategoryMappingEditor): Single `ChevronDown` with `-rotate-90` when collapsed. `transition-transform duration-200` for smooth animation.
        - **Pattern B** (Transactions `CategoryGroupRow`, `SparklineCard`): Conditional render of `ChevronDown` vs `ChevronRight`. No animation.
      Standardize on Pattern A. Update `CategoryGroupRow` in `TransactionsPage.tsx` and `SparklineCard` to use single `ChevronDown` + rotation. Consider extracting an `ExpandChevron` component if the pattern repeats in 4+ places.
    - Why: Two different expand/collapse animations for the same interaction is a subtle but real inconsistency. The animated rotation is better UX (smooth state transition) and fewer components.

- [ ] **Section heading standardization**
    - Effort: S
    - Dependencies: v0.10.2
    - What: Standardize all section headings app-wide on the "heading + description" pattern from Insights (v0.8.5). Format: `<h2 className="mb-1 font-medium text-lg text-foreground">` + `<p className="mb-4 text-xs text-muted-foreground">`. Sections that currently lack descriptions: Dashboard ("Month History"), Transactions ("Transactions", "Category Breakdown"), Settle Up ("Record Payment", "Payment History"). Write a one-line description for each that explains *why* the section is useful, not *what* it contains.
    - Why: Headings with descriptions are warmer and more helpful than bare titles. The pattern exists on newer pages — extend it everywhere.
    - Notes: Don't add descriptions to sections where one would feel forced (e.g., the settlement hero card is self-explanatory). Use judgment — the goal is helpfulness, not uniformity for its own sake.

- [ ] **Form label unification**
    - Effort: XS
    - Dependencies: none
    - What: Audit all standalone form labels. Two patterns exist: `text-sm font-medium text-foreground` (SettleUp, TransactionEditor) and `text-xs font-medium text-muted-foreground` (Budget AddBudgetForm). Standardize on `text-sm font-medium text-foreground` — it's more readable and used in more places. Inline editor labels (`text-sm text-muted-foreground` with `w-16 shrink-0`) are intentionally compact and stay as-is.
    - Why: One label style for all standalone forms. Inline/compact labels remain distinct because they serve a different purpose.

#### Touch & Mobile Polish

- [ ] **Touch target audit**
    - Effort: M
    - Dependencies: v0.10.1, v0.10.2
    - What: Audit every interactive element for the 44px minimum touch target (WCAG 2.5.8). Known violations:
        - Icon buttons (`p-1.5` + `size-3.5`/`size-4` = ~24–28px): rename, delete, icon picker triggers in Settings; sort indicators in Transactions; delete payment in Settle Up. Fix: increase to `p-2.5` or add transparent hit area padding.
        - Checkboxes (`size-4` = 16px): bulk edit mode in Transactions. Fix: wrap in a `min-h-11 min-w-11 flex items-center justify-center` container, or increase the checkbox size on mobile.
        - Filter pills: currently small text buttons. Ensure minimum height of 44px on mobile.
      Desktop sizes can stay compact (the 44px minimum is for touch devices). Use `sm:p-1.5` to keep desktop compact, `p-2.5` for mobile.
    - Why: Touch targets below 44px cause tap errors. Every icon button in the app is currently below minimum.
    - Notes: The `Button` component already meets minimum (`min-h-11`). The issue is icon-only buttons and checkboxes.

- [ ] **Popover → sheet conversion on mobile**
    - Effort: M
    - Dependencies: v0.10.1 (DateRangePicker mobile modal)
    - What: Extend the sheet pattern from v0.10.0 ("More" sheet) and v0.10.1 (DateRangePicker modal) to remaining popovers:
        - **MonthPicker** (`MonthPicker.tsx`): dropdown `absolute right-0 top-full` clips on mobile. Convert to bottom sheet below `sm:`.
        - **Filter dropdowns** (`TransactionFilters.tsx`): CategoryFilter, TagFilter, AmountRangeFilter all use `FilterPopover` with absolute positioning. Below `sm:`, open as bottom sheets.
        - **IconPicker**: already handled in v0.10.2.
      Extract a shared `ResponsivePopover` component: renders as an absolute-positioned popover above `sm:`, bottom sheet below `sm:`. Reuse across all popovers.
    - Why: Popovers that work on 1440px desktops clip or overflow on 375px phones. Bottom sheets are the standard mobile alternative.
    - Notes:
        - `ResponsivePopover` should accept `trigger` (the button) and `content` (the dropdown/sheet body). It handles the breakpoint detection and positioning internally.
        - Desktop behavior is completely unchanged — no regression risk for the primary laptop workflow.

- [ ] **Focus and hover state consistency**
    - Effort: S
    - Dependencies: none
    - What: Audit all interactive elements for consistent focus and hover states:
        - Focus: all clickable elements should show the `outline-2 outline-ring` focus ring. Check icon buttons, card rows, filter pills, navigation items.
        - Hover: standardize on `hover:bg-muted/50` for card-like rows (month history, payment history, transaction rows). Currently mixed: some use `hover:bg-muted`, others `hover:bg-muted/50`, others `hover:underline`.
        - No hover-only interactions: anything revealed on hover must also be accessible via tap or always-visible on mobile (e.g., action buttons in Settings group cards).
    - Why: Inconsistent hover states make the app feel assembled from parts. Missing focus states are an accessibility violation.

## Design Rationale

**Why four releases, not one or two**: The original v0.10.0 bundled everything into three tasks. That's too coarse for this scope — each task would be a multi-day effort with tangled concerns (shell + content + polish). Four releases match the v0.8.x cadence: each is independently shippable, testable in a few hours, and focuses on one concern. v0.10.0 is the foundation. v0.10.1 is page content. v0.10.2 is the worst page. v0.10.3 is the cross-cutting pass.

**Why content pages before Settings**: Dashboard, Transactions, and Settle Up are the monthly-ritual pages — used every month during solo prep and the together session. Settings is "occasionally, not monthly" (per user flows). Mobile value is proportional to visit frequency. The couple will test "does this work on my phone?" on the Dashboard first.

**Why touch polish is last, not first**: Touch targets affect every interactive element across every page. Doing them after all layout work avoids rework — if a component moves or changes during v0.10.0–v0.10.2, touch target adjustments would need to be redone. Batch the cross-cutting pass when layouts are stable.

**Why 5+More bottom nav, not all 7**: Seven items in a bottom tab bar gives each tab ~53px on a 375px phone — below the 44px touch target but cramped with icon+label. The 5+More pattern (Dashboard, Transactions, Settle Up, Budget, Insights as primary; Upload, Settings, identity in a "More" sheet) keeps primary destinations one tap away and secondary destinations two taps away. Upload and Settings are low-frequency (monthly solo prep). The identity toggle is rarely used (each person uses their own laptop). This matches the information architecture: the five primary pages are the monthly workflow; the remaining items are support.

**Why no container queries**: Every responsive component in this app lives inside a known page container (`max-w-4xl` or `max-w-3xl` centered). No component is reused at wildly different parent widths. Media queries are sufficient and simpler. Container queries add complexity (containment context, size tracking) for zero benefit in this layout architecture. If a component ever needs parent-relative responsiveness (e.g., `StatsGrid` in a sidebar), revisit then.

**Why consistency audit is bundled with touch polish**: Both require touching the same components. Chevron unification, heading standardization, touch target expansion, and hover state cleanup are all "open the file, fix three things, close the file" changes. Splitting them means opening the same files twice for no benefit.

**Why the Settings overhaul is desktop+mobile**: The CategoryMappingEditor is cramped and awkward at *any* viewport. Fixing it only for mobile would mean a second quality pass later for desktop. Designing the component once for both contexts (responsive from the start) is less total work and avoids the consistency gap that created the current problem.
