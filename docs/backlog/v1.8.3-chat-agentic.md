# v1.8.3 — Agentic Chat: Code Execution + Subagent

Status: Planned
Effort: L
Depends on: v1.8.1 (read tools — the subagent's toolset), v1.8.2 (optional)
Series overview: [v1.8.x — Agentic Chat](v1.8.x-agentic-chat.md)

## Goal

Give the assistant real agentic capability: a server-side Python sandbox
that calls the app's read tools programmatically (fetch → filter → aggregate
in code, so only answers enter model context), and a fresh-context research
subagent for open-ended analysis that would flood the main conversation.
Both are additive tools in the registry (`kind="agentic"` — extend the
`ToolSpec.kind` Literal). This version also adopts tool search
(`defer_loading`) and context management — it is where tool counts and turn
counts multiply, so the context-growth work lands here.

Division of labor between the two agentic capabilities: programmatic tool
calling is for computation and aggregation over known data ("sum my Q1
groceries", projections, what-if math); `delegate_analysis` is for
open-ended multi-search *reasoning* ("find anomalies this year") where the
value is fresh-context judgment, not arithmetic.

## Learnings from v1.8.1/v1.8.2 (read before planning)

Facts established while shipping the previous two versions that change or
sharpen tasks below:

- **`strict: true` was tried and abandoned — no schema sets it.** Three
  live-verified API limits at this registry's size (31 tools): (1) at most
  20 strict tools per request; (2) even 16 strict write tools 400'd on
  compiled-grammar size ("The compiled grammar is too large"); (3) strict
  rejects numeric/array constraints ("properties maximum, minimum are not
  supported"). Handler validation is the boundary guard instead; schemas
  keep `additionalProperties: false` and prose ranges
  (`test_no_strict_schemas`,
  `test_no_numeric_or_array_constraints_in_schemas` pin both). Upside for
  this version: `allowed_callers` (incompatible with strict per current
  docs, as are `disable_parallel_tool_use`, forced `tool_choice`, and MCP
  tools) can go on read tools with no strict conflict. Do NOT reintroduce
  strict when adding tools.
- **Smoke-test the tool list against the live API early.** Only a real API
  call catches schema-shape rejections (unit tests can't). A propose-only
  smoke (never confirming) is safe against real data. The v1.8.1/v1.8.2
  smoke flow: mint a short-lived session token with
  `src.infrastructure.auth.tokens.create_access_token` + the person id from
  `list_persons`, then curl the SSE endpoint.
- **`pause_turn` handling already shipped in v1.8.0** (`use_case.py`), with
  tests (`test_pause_turn_resumes_with_assistant_echo`,
  `test_pause_turn_is_bounded_by_max_turns`). The "Loop change" item in
  Part 1 is verify-only.
- **`ToolSpec` has no `kind` field.** Read vs. write is derived from
  `executor is None`. Part 1's registry groundwork adds the explicit
  `kind` Literal (or keeps deriving — decide then), plus `allowed_callers`
  and `defer_loading` fields.
- **Tool names now carry the read/write convention.** The frontend derives
  its "Looking up… vs Proposing…" indicator from the name
  (`isMutationTool` in `ToolCallIndicator.tsx`: mutation = not `get_*` /
  `search_*`), and `test_read_write_naming_convention` pins it in the
  registry shape test. `delegate_analysis` breaks that rule by name — when
  adding `kind="agentic"`, exempt agentic tools in the shape test and teach
  `isMutationTool` about them (delegate_analysis reads, it must render as a
  lookup, not a proposal).
- **Untrusted-content labeling is now systematic.** `_user_str()` wraps
  every user-originated string in tool results; the system prompt's
  `<untrusted_content>` block tells the model wrapped values are data, and
  to strip the tags when reusing a value as tool input. The
  `delegate_analysis` subagent's own system prompt needs the same block,
  and sandbox code calling read tools programmatically will see wrapped
  values — account for that in the sandbox guidance.
- **Cache breakpoints: all placements are live.** system (1) + last tool
  (1, stamped in `_build_tools`) + last message (1, `_with_incremental_cache`)
  = 3 of 4 used. Part 3's tool-search work must re-derive placement from
  the tool-search docs and update `test_only_last_tool_carries_cache_control`.
- **Registry entries with `use_cases=()` are fine.** The parity test only
  checks that discovered use cases are classified — a server-tool entry
  (code_execution) with no use cases doesn't trip it. Note
  `PENDING_PARITY_USE_CASES` no longer exists (deleted in v1.8.2).

## Context for a fresh agent

- Config lives in `ChatConfig` (`src/config/settings.py`). Add:
  `enable_code_execution: bool = True`, `subagent_max_turns: int = 12`,
  `subagent_effort: str = "low"` (add fields only when used — vulture).
  Current effort docs recommend `low` for subagents and `xhigh` for main
  agent loops — consider bumping `ChatConfig.effort` from `"high"` in the
  same change, judged against real latency/cost (verify exact enum values
  against the effort docs at implementation).

## Part 1 — Code execution sandbox + programmatic tool calling

- Tool type is `code_execution_20260120` (REPL persistence + programmatic
  tool calling, Opus 4.5+, GA, **no beta header**). The newer
  `code_execution_20260521` variant is also GA on the API — check what SDK
  0.97 actually exposes at implementation time and prefer the newest
  available. Append `{"type": "code_execution_20260120", "name":
  "code_execution"}` to the tool list when `enable_code_execution` — as a
  registry entry with `use_cases=()` so the parity test stays clean. Note the
  cache_control breakpoint must stay on the LAST tool entry (`_build_tools`).
- **Programmatic tool calling** (the point of this part): every read
  `ToolSpec` sets `allowed_callers: ["code_execution_20260120"]`, so the
  sandbox can call read tools directly and filter/aggregate their results in
  code — only the final numbers enter model context (a year of transactions
  never transits the conversation). Write tools and `delegate_analysis` are
  NEVER exposed via `allowed_callers` (see v1.8.2) — the registry shape test
  asserts this split. Mechanically, programmatic calls still surface as
  `tool_use` blocks the existing loop executes; their results route back into
  the sandbox rather than model context — verify the SDK 0.97 block shapes
  and pin them with adapter tests.
- **Loop change** (`use_case.py`): handle `stop_reason == "pause_turn"` —
  append `{"role": "assistant", "content": response.raw_content}` to messages
  and continue the loop WITHOUT tool_results (the server resumes
  automatically). Counts against `max_turns`.
- **Adapter stream events**: on `content_block_stop`, in addition to
  `ToolUseBlock`, yield application events for `ServerToolUseBlock`
  (→ `ServerToolStartEvent(name, input)`) and
  `BashCodeExecutionToolResultBlock` (→ `ServerToolResultEvent(stdout,
  stderr, return_code)`, stdout/stderr truncated to ~2KB). Add both to
  `src/application/chat/events.py` and the `ChatEvent` union; pass through
  the use case's event loop and `_bridge`.
- **SSE protocol additions** (backend `sse.py` serialization + frontend
  `chat-sse.ts`): `{"type": "code_start", id, command}` and
  `{"type": "code_result", id, stdout, stderr, return_code}`.
  `TERMINAL_TYPES` unchanged.
- **Frontend**: `CodeExecutionCard.tsx` — monospace command, collapsible
  output; new store fields + callbacks; vitest.
- **System prompt** (`system_prompt.py`): add sandbox guidance — "For
  multi-step analysis, projections, and what-if math, prefer running code:
  call the read tools from inside the sandbox, filter and aggregate there,
  and return only the result to the conversation. Don't paste large tool
  outputs through the chat when code can process them."
- Container reuse across POSTs: deferred. Stateless per request is fine.
  Pricing: containers bill ~$0.05/hour beyond a free tier (verify current
  numbers) — negligible at this app's usage.
- Data note (decided): chat data already transits Anthropic; the sandbox is
  not a new exposure. Programmatic read-tool calls return the same data the
  model would otherwise see inline.

## Part 2 — `delegate_analysis` subagent

- New `src/application/chat/subagent.py`:
  `async def run_subagent(question, scope, llm, current_user, persons) -> str`.
  - Fresh `messages` list; own system prompt: research subagent for a
    couples-finance app, investigate with read tools, return a dense
    self-contained summary under ~1,500 tokens with concrete figures and IDs
    (matches Anthropic's 1–2K condensed-summary guidance for subagents).
  - Toolset = read tools only, derived from the registry
    (`[spec for spec in REGISTRY if spec.kind == "read"]`) — no mutations, no
    code execution, no nested delegate_analysis (one level).
  - Reuse `ChatUseCase` with a `ChatCommand` carrying
    `max_turns=subagent_max_turns`, `effort=subagent_effort`; consume its
    events internally (log tool calls, accumulate TextDeltas); the
    accumulated final text IS the tool result. Optionally return the summary
    via structured outputs (`output_config` format, GA) instead of
    accumulated free text — decide at implementation; free text is
    acceptable.
  - On `MaxRoundsExceededError`: return the partial accumulated text prefixed
    with "[Analysis truncated at turn limit — findings so far:]" (an
    actionable result for the main model, not an exception).
- Handler needs the LLM client, which handlers don't receive today: extend
  the handler signature to a context object —
  `ToolContext(current_user, persons, llm)` — updating `registry.execute_tool`,
  all existing handlers (mechanical), and `use_case.py`'s call site. Keep it
  a frozen dataclass in `registry.py` or `protocols.py`.
- Tool schema: `delegate_analysis(question: str, scope?: str)`. Description
  trigger (Opus 4.8 under-delegates by default): "Call this for open-ended
  analysis that would need many searches — 'review our whole year and find
  anomalies', 'audit our splits for mistakes' — so the main conversation
  stays focused. Do NOT call it for questions one or two tools can answer."
- SSE: a single normal `tool_start`/`tool_result` pair (summary dict
  `{"summary": "..."}`). Nested progress events are out of scope.
- System prompt: add delegation guidance mirroring the tool description.

## Part 3 — Tool search (`defer_loading`)

Anthropic recommends tool search at **10+ tools**; after v1.8.2 the registry
holds ~33, and the measured effect is tool-selection accuracy, not just
tokens (Opus MCP evals 79.5% → 88.1% in the advanced-tool-use post).

- `ToolSpec` gains `defer_loading: bool = False`. Keep the 3–5 hot tools
  loaded up front (`search_transactions`, `get_settlement_balance`,
  `get_budget_overview` — adjust from observed traffic); every other tool
  sets `defer_loading=True`.
- `_build_tools` emits the tool-search tool plus per-tool `defer_loading`
  flags; deferred discovery preserves the prompt cache. Revisit the
  cache_control breakpoint currently pinned to the last tool entry and update
  the registry shape test to whatever placement the tool-search docs
  prescribe.
- `code_execution` and `delegate_analysis` stay non-deferred — they are the
  capabilities Opus 4.8 most under-reaches for.

## Part 4 — Context management

Turns multiply in this version (pause_turn continuations + a subagent
sub-loop), so in-conversation context growth is addressed here. The
message-array cache breakpoint shipped in v1.8.1; this adds eviction:

- Add `context_management` with `clear_tool_uses_20250919` (**BETA** —
  header `anthropic-beta: context-management-2025-06-27`): clear oldest tool
  results past a token trigger, keeping the most recent ~3 tool pairs. Tune
  `clear_at_least` so each cache invalidation buys enough savings; keeping
  thinking blocks preserves the prompt cache.
- Evaluate server-side `compact_20260112` (Jan 2026 — preferred over
  client-side compaction, which is deprecated) for long chats. Likely
  overkill under the frontend's 50-message history cap — decide from real
  transcripts, and record the decision here either way.

## Deliberately out of scope (do not build)

- Namespacing renames (frontend TOOL_LABELS/card churn for no measured gain).
- Memory tool / cross-session persistence (needs storage + person-scoping
  design — lives in `unscheduled.md`). Note for that future design:
  persistent memory is a prompt-injection reinfection vector (Anthropic
  containment write-up, May 2026) — plan startup-phase scanning of persisted
  state.
- Parallel subagent orchestration.
