# v1.14.x: Hosting

For strategic overview, see the [planning overview](README.md).

## Why this version

The app only ran on two laptops. Using it meant a checkout, a Python 3.14
toolchain, and a terminal left running — so in practice one person could use it
and the other waited to be shown. It also let the two laptops drift to
different code versions against the same Neon database, which is the reason the
schema-version guard exists at all. This series puts the app at a URL.

The sister project mixd already solved this with the same stack, so the shape
is a port rather than a design: one container, FastAPI serving the built
frontend from its own origin, Neon unchanged, Fly.io in front.

Serving the frontend same-origin is what keeps the change small. The existing
session cookie and every `/api` fetch already use relative paths, so nothing
under `web/src` changes and CORS never comes into play.

### v1.14.0: Fly.io hosting
**Goal**: Both people open a URL. No checkout, no terminal, no version drift.
**Status**: Completed (2026-09-06)
**Context**: No `Dockerfile`, no `fly.toml`, no `.github/` at all. Three things
in the tree would have broken a container quietly: `alembic.ini` hardcoded a
localhost URL that the CLI prefers over settings; the startup seed read
`data/category_groups.json`, which is gitignored, so a fresh database would
crash the lifespan; and the Fly health check had only a database-querying
endpoint to point at, which would have held Neon's compute out of autosuspend
permanently.

- [x] **Startup path fit for a container**
    - Effort: S
    - What: `alembic.ini`'s `sqlalchemy.url` is commented out so `env.py` falls
      back to settings (the CLI previously always targeted localhost);
      `run_migrations` resolves `script_location` absolutely rather than
      relative to the working directory; a committed generic seed taxonomy
      makes a fresh database bootable (see the story below);
      `LoggingConfig.file_path` makes the rotating file sink opt-in,
      defaulting to stdout only.
    - Why: Each one fails silently rather than loudly — a wrong database, a
      crash on first boot, or a write-only log on a disk that disappears.
    - Dependencies: None
    - Status: Completed (2026-09-06)

- [x] **A generic seed taxonomy for fresh databases**
    - Effort: S
    - What: `src/application/use_cases/seed_data/category_groups.json` holds
      Monarch's 15 default groups and their standard categories, committed with
      the code. `data/category_groups.json` stays gitignored and takes
      precedence when present, so the couple's laptops are unaffected.
    - Why: The seed previously read a gitignored file, so any environment
      without it crashed on first boot. Committing the household's own taxonomy
      instead would have published it — the repository is public, and the
      groups are personal (Playa, Festivals). Seeding is skipped entirely once
      a database has groups, so neither fixture can disturb existing data.
    - Dependencies: None
    - Status: Completed (2026-09-06)

- [x] **The API serves the frontend**
    - Effort: S
    - What: `_mount_static` in `src/interface/api/app.py` mounts `/assets` and
      registers a catch-all that serves real files, falls back to `index.html`
      for client routes, and re-raises `NotFoundError` for `/api` paths.
      Registered last, after every router. A no-op when `web/dist` is absent,
      so `pnpm dev` and CI are unaffected.
    - Why: Same-origin is what lets the session cookie and the relative `/api`
      paths work in production with no frontend change and no CORS.
    - Dependencies: None
    - Status: Completed (2026-09-06)

- [x] **Database-free liveness probe**
    - Effort: XS
    - What: `/api/v1/health/live` returns `{"status": "ok"}` without touching
      the database, `include_in_schema=False` so it stays out of the generated
      client. `/api/v1/health` is untouched — the frontend gates on its
      `schema_ok`.
    - Why: A 30s probe against the deep endpoint would reset Neon's autosuspend
      timer forever, and a brief database outage would restart the machine into
      a startup path that needs the same database.
    - Dependencies: None
    - Status: Completed (2026-09-06)

- [x] **Container image and Fly configuration**
    - Effort: M
    - What: Three-stage `Dockerfile` (uv venv, pnpm bundle, slim non-root
      runtime), an allowlist `.dockerignore`, and `fly.toml` — one machine in
      `sjc`, `auto_stop_machines = 'off'`, health check on `/health/live`,
      SIGTERM with a 60s kill timeout. Version pins added where none existed:
      `[tool.uv] required-version`, `packageManager`, `.node-version`.
    - Why: One machine is a hard requirement, not a cost choice — the SSE event
      bus and the chat rate limiter are both in-process. No `release_command`:
      migrations already run in the lifespan, and a failed one already aborts
      the release.
    - Dependencies: Startup path fit for a container
    - Status: Completed (2026-09-06)

- [x] **CI and tag-triggered release**
    - Effort: M
    - What: `ci.yml` (Python gate against a per-PR Neon branch, web gate,
      Docker build), `release.yml` (`v*` tag → GitHub Release from
      `CHANGELOG.md` → `flyctl deploy`), `neon-cleanup.yml`. New root
      `CHANGELOG.md`; the project adopts `release-per-ship` mode.
    - Why: The Docker build job exists specifically so a broken image fails on
      a PR rather than after a public tag is already published.
    - Dependencies: Container image and Fly configuration
    - Status: Completed (2026-09-06)

#### Known characteristics

- A deploy with a browser tab open pauses up to 30s. `/api/v1/events` never
  ends on its own and uvicorn drains connections before lifespan shutdown, so
  an in-app shutdown signal would arrive too late; the graceful-shutdown
  timeout is the only bound. Not lower because chat replies stream for tens of
  seconds. See `docs/deployment.md`.
- A wrong-method call to an API path now returns 404 rather than 405, because
  the catch-all fully matches where the real route only partially matched.
  Authentication status codes are unaffected.
