# v1.12.x: Insights Scope

For strategic overview, see the [planning overview](README.md).

## Why this version

Budget ("My Budget", v0.11.3) and Dashboard ("My spending", v1.2.0) can answer
"what did *I* spend?" — each person's share of household rows plus their
personal rows plus what their partner spotted for them. Insights could not: it
was hardwired to household rows at their full amount, so the one page built for
trend conversations showed a number that belonged to neither person. This
series gives Insights the same scope toggle, computed by the same domain rule,
so the three pages cannot disagree about a person's spending.

### v1.12.1: Transfer-kind category groups
**Goal**: Credit card payments and account transfers stop counting as spending, everywhere at once, with the rule living on the category group the couple already maintains.
**Status**: Completed (2026-09-03)
**Context**: Insights showed a "Transfer" group at $73k YTD from the Monarch category "Credit Card Payment". Monarch's CSV drops its category type, and couplefins had no notion of a group that is "not spending" — the seeded Transfer group was ordinary. Budget's "My Budget" and the Dashboard's "My spending" had the same hole; the v1.12.0 personal lens made it visible. Monarch, Copilot, Tiller, Lunch Money, and Rocket Money all solve this with a category type evaluated at read time: transfers excluded from spending and budgets, still visible with a marker.

- [x] **Group kind in the domain and everywhere spending is computed**
    - Effort: M
    - What: `CategoryGroup.kind` (`expense` | `transfer`), `get_transfer_categories` in `src/domain/categories.py`, `exclude_transfers` (renamed `exclude_non_spending` in v1.13.3) in `src/domain/filters.py`, and `ReconciliationContext.transfer_categories`. Applied right after fetching in budget overview, dashboard, spending trends (target and comparison year), `load_ledger` (the settle-up / record / waive / chat chokepoint), reconciliation math (the returned list keeps transfers for the Transactions page), and adjustment export. Budget builds status rows for expense-kind groups only; `save_budget` rejects transfer groups; switching a group to transfer is rejected while it has budgets. The candidate finder is deliberately unfiltered so Venmo legs in the Transfer group stay candidates.
    - Why: One read-time rule, same reach as `is_excluded`, never stamped on rows — moving a category between groups corrects history too.
    - Dependencies: None
    - Status: Completed (2026-09-03)

- [x] **Persistence, API, seed, and chat**
    - Effort: S
    - What: Migration `0013_category_group_kind` adds the column with a check constraint and flips any group named "Transfer" (dropping its budgets, which a transfer group never carries) so prod is corrected on deploy; the seed fixture marks the Transfer group. `kind` on the category-group create (default expense), update (required — a chat rename that forgot it would silently reset the Transfer group), and list responses. `get_category_setup` reports each group's kind and the transfer categories.
    - Why: Existing installs need no settings visit; new installs start correct.
    - Dependencies: Group kind in the domain
    - Status: Completed (2026-09-03)
    - Notes: No chat write tool for kind yet; `manage_category_group` could gain a `set_kind` action if it comes up in conversation.

- [x] **Settings control and Transactions badge**
    - Effort: S
    - What: Settings → Category Groups shows a "Counts as: Spending | Transfer" control per group with a caption on transfer groups and a collapsed "Transfer" pill; the add-group form offers the same choice; rename and icon edits carry `kind`. Transactions derives the transfer set from the already-loaded groups (`transferCategoriesOf`), shows a "Transfer" badge on those rows, keeps them only under All, and leaves them out of the Imported buckets (new "Transfer" line) and the In view total.
    - Why: Excluded, not hidden — the couple can always see where the money went and why it is not counted.
    - Dependencies: Persistence, API, seed, and chat
    - Status: Completed (2026-09-03)
    - Notes: `settlement_matching._TRANSFER_KEYWORDS` still scores candidates by category-name substrings; a kind-based score is a small follow-up once that path receives `ctx`. Migration flips by the exact name "Transfer"; any other transfer-like group needs the Settings toggle.

### v1.12.2: One source of truth for spending rows and person share
**Goal**: The transfer rule cannot be forgotten, and Budget, Insights, and the Dashboard compute "spending" through one domain lens and one accumulator — agreeing exactly for the same rows, except that Budget's household view additionally admits `include_personal` categories (US-BUDGET-4).
**Status**: Completed (2026-09-05)
**Context**: After v1.12.1, `exclude_transfers` (renamed `exclude_non_spending` in v1.13.3) was applied in Python at nine application sites right after each fetch — a new use case that fetched rows and did money math would silently count card payments again. Budget and Insights also carried two personal-spending predicates (Budget kept `$0`-share household rows as `$0` rows; Insights dropped them), two breakdown accumulators, and a third loop on the Dashboard; Insights was the only computation that dropped refunds. Research compared repository SQL, a typed rows object, entity hydration, and an application read-model; the read-model with a grep gate closed every site without changing the domain's signatures.

- [x] **Transaction reads module**
    - Effort: M
    - What: `src/application/use_cases/_shared/transaction_reads.py` is the only module that reads transaction lists. Each function names its rows (`fetch_year_spending_rows`, `fetch_all_settlement_rows`, `fetch_settlement_rows`, `fetch_scoped_rows` → `ScopedRows(listed, spending)`, `fetch_listed_rows`) and applies `exclude_transfers` (renamed `exclude_non_spending` in v1.13.3) once. `GetReconciliationResult` carries `spending_transactions` next to the listed rows. Two grep gates in `tests/unit/application/test_transaction_reads.py` fail the build if any other application module calls a list-read repository method or imports `exclude_transfers` (renamed `exclude_non_spending` in v1.13.3).
    - Why: Forgetting the rule is a red test, not a review catch — the same way the repo already guards `is_reconciliation_relevant`.
    - Dependencies: v1.12.1
    - Status: Completed (2026-09-05)

- [x] **One spending lens**
    - Effort: M
    - What: `src/domain/spending_lens.py` — `HouseholdLens(personal_categories)`, `PersonalLens(person_id)`, `SplitLens()` behind a `SpendingLens` protocol (`is_relevant`, `contribution`, `personal_owner`), plus `select`, `total_spending`, `compute_breakdowns` (the single accumulator) and `source_split`. Budget's two overviews collapse into `compute_budget_overview(inputs, lens)`; Insights, `reconcile()`, and the Dashboard's personal figures and household card all go through the lens. `compute_category_breakdowns`, `compute_personal_category_breakdowns`, `is_personal_spending_relevant`, and the personal-overview variants are deleted. `tests/unit/domain/test_spending_parity.py` pins Budget == Insights == Dashboard per group and per lens on one mixed fixture.
    - Why: Product decision: a household row with no share for the viewer belongs to the household view only (each partner's own concert ticket). One predicate, one accumulator, one refund rule.
    - Dependencies: None
    - Status: Completed (2026-09-05)
    - Notes: Behavior changes — Insights now nets refunds (a refund-only group/month can go negative); "My Budget" no longer lists partner-paid `$0`-share household rows (counts drop, amounts unchanged); the Budget average hint nets refunds; the Dashboard household card nets refunds; household Budget responses now populate `household_spending`/`personal_spending`; the Dashboard "all" scope nets refunds through `AllRowsLens` (every reconciliation-relevant row at full amount, personal rows attributed to their payer), so "all" can never read below "household" for the same rows. The Budget average-per-month divisor is the number of months with any row under the lens — a refund-only month counts, a month with no rows does not.
