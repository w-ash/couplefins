### v1.0.0: Infrastructure Investigation
**Goal**: Measure current performance, audit database capabilities, and make evidence-based decisions on storage and indexing strategy.
**Context**: Tags are stored as JSON strings in a `String` column (`tags_json`) with no index and no server-side filtering. `get_distinct_tags()` fetches every distinct JSON array and unions them in Python. This works fine at ~200 transactions/month, but it's architecturally fragile — and before optimizing, the couple needs data on where the actual bottlenecks are (or aren't). The app also runs on SQLite, which is great for local development but limits deployment options and concurrent access. This investigation phase answers: what's actually slow, what's fine, and what should change.
**What this unlocks**: Every decision in v1.0.1–v1.0.3 is backed by benchmark data rather than guesswork. If the investigation shows current performance is adequate at projected scale, "do nothing yet" is a valid outcome worth the small investment to reach with confidence.
**Key tech choices**: `pytest-benchmark` for reproducible measurements. Realistic data seeding at multiple scales (1yr, 2yr, 10yr of transactions). SQLite 3.46+ JSON capabilities tested through the actual aiosqlite + SQLAlchemy stack, not just raw SQL.

#### Benchmarking

- [ ] **Performance benchmark suite**
    - Effort: S
    - Dependencies: v0.9.1
    - What: Create `tests/benchmarks/` with a data seeder that generates realistic transactions at three scales: current (2,400 txns / 12 months), 2x (4,800 / 24 months), and stress (24,000 / simulating years of history). Benchmark these operations at each scale: `get_distinct_tags()`, transaction batch deserialization (`json.loads` on `tags_json` for 200+ rows), full reconciliation query for a single month, and simulated server-side tag filtering. Use `pytest-benchmark` or manual timing with the `performance` marker already in `pyproject.toml`.
    - Why: Without numbers, optimization is guessing. The benchmark suite also serves as a regression guard for future changes.
    - Notes:
        - Seeder should produce realistic tag distributions: ~80% of transactions have `["shared"]`, ~15% have `["shared", "s70"]` or similar, ~5% have 3+ tags
        - Include both hot-cache and cold-cache runs
        - Measure wall time and query count (detect N+1 patterns)

#### Database Audit

- [ ] **SQLite JSON capability audit**
    - Effort: S
    - Dependencies: v0.9.1
    - What: Verify which SQLite JSON functions work through the aiosqlite + SQLAlchemy async stack. Test: `json_each()` as a virtual table in joins, `json_extract()` for scalar access, expression indexes on JSON paths, and JSONB support (SQLite 3.45+). Document what requires `sqlalchemy.text()` raw SQL vs. what works through the ORM. Check the exact SQLite version bundled with Python 3.14's `sqlite3` module.
    - Why: SQLite's JSON support has improved dramatically since 3.38 (2022), but capabilities vary by version and driver. Knowing what actually works through our stack determines whether SQLite-native optimization is viable or if we need schema changes.

- [ ] **Full index review**
    - Effort: S
    - Dependencies: "Performance benchmark suite"
    - What: Audit all existing indexes (`ix_transactions_shared_date`, `ix_transactions_upload_id`, `ix_transactions_person_date`) against actual query patterns from use cases. Run `EXPLAIN QUERY PLAN` on the top 10 most-executed queries. Identify: missing indexes (e.g., no tag index, no `is_settlement` index), unused indexes, covering index opportunities, and partial index candidates.
    - Why: Indexes are the highest-leverage, lowest-risk performance improvement. A systematic audit prevents ad-hoc index additions.

#### Evaluation

- [ ] **Storage and database evaluation**
    - Effort: M
    - Dependencies: "SQLite JSON capability audit", "Full index review"
    - What: Using benchmark data and the capability audit, compare four approaches for tag storage and querying:
        1. **SQLite + `json_each()`** — keep `tags_json`, query with JSON functions, add expression indexes where possible
        2. **SQLite + normalized tables** — new `tags` + `transaction_tags` junction table, standard B-tree indexes
        3. **PostgreSQL + JSONB + GIN** — migrate database, use `tags jsonb` column with GIN index for `@>` containment queries
        4. **PostgreSQL + normalized tables** — migrate database, normalize tag storage

      Evaluate each on: query performance (from benchmarks), schema migration effort, deployment complexity, feature enablement (tag rename/merge/stats), and alignment with projected scale (~2 people, ~200 txns/month, years of history). Produce a short decision document in `docs/decisions/` with the recommendation.
    - Why: The "right" answer depends on whether PostgreSQL migration is coming. If it is, JSONB+GIN might be simpler than normalization. If not, normalized tables are more portable. This decision affects v1.0.1 and v1.0.2.
    - Notes:
        - PostgreSQL GIN indexes on JSONB arrays are the gold standard for this pattern (`tags @> '["shared"]'` is O(log n))
        - But PostgreSQL adds deployment complexity (connection pooling, managed service or self-hosted, backups)
        - SQLite's `json_each()` can't be indexed for element membership — it's a virtual table, so queries are effectively filtered scans
        - Weigh the "do nothing" option honestly — at 200 txns/month, current approach may be fine for the app's entire lifetime

### v1.0.1: Query & Storage Optimization
**Goal**: Ship the highest-impact improvements within the current SQLite setup, based on investigation findings.
**Context**: v1.0.0 produced benchmark data, a capability audit, and a storage recommendation. This version implements the "quick wins" — changes that improve performance and developer ergonomics without requiring a database migration or schema redesign.
**What this unlocks**: Server-side tag filtering, faster tag queries, and a systematically optimized index set. These improvements are database-agnostic and carry forward to PostgreSQL if/when that migration happens.

#### Tag Queries

- [ ] **`get_distinct_tags()` via `json_each()`**
    - Effort: S
    - Dependencies: v1.0.0
    - What: Replace the current Python-side approach in `TransactionRepository.get_distinct_tags()` — which does `SELECT DISTINCT tags_json` then `json.loads()` in a loop — with a single SQL query: `SELECT DISTINCT value FROM transactions, json_each(tags_json)`. The repository method signature stays the same (`async def get_distinct_tags(self) -> list[str]`). Use `sqlalchemy.text()` for the raw SQL.
    - Why: Pushes deduplication to SQLite, eliminates Python-side JSON parsing, and reduces data transfer. At scale, this is O(rows) in the database vs. O(distinct_json_arrays * avg_tags_per_array) in Python.

- [ ] **Server-side tag filtering**
    - Effort: M
    - Dependencies: "`get_distinct_tags()` via `json_each()`"
    - What: Add optional `tags` query parameter to the transactions/reconciliation endpoint. SQL filter: `WHERE EXISTS (SELECT 1 FROM json_each(tags_json) WHERE value IN (:tags))`. The frontend `useTransactionFilters` hook stays client-side for instant interaction, but the initial data fetch can be scoped by tag when the user navigates with a tag pre-selected (e.g., deep-linking from a tag chip).
    - Why: Reduces payload size when filtering by tag. Foundation for future tag-based views (e.g., "show all settlement-tagged transactions").

#### Indexing

- [ ] **Index additions from audit**
    - Effort: S
    - Dependencies: v1.0.0
    - What: Implement the index changes recommended by the v1.0.0 full index review. Likely candidates: partial index on `tags_json` for non-empty tags (`WHERE tags_json != '[]'`), index on `is_settlement` if settle-up queries benefit, and any covering indexes identified by `EXPLAIN QUERY PLAN` analysis. Alembic migration for each index change.
    - Why: Indexes are the highest-ROI optimization — minimal code change, significant query improvement.

#### Query Patterns

- [ ] **Sequential query batching**
    - Effort: S
    - Dependencies: v1.0.0
    - What: Review and batch sequential database calls identified during investigation. Known candidates: `validate_settlement_persons()` makes two sequential `get_by_id()` calls that could be a single `get_by_ids()`. Audit all use cases for similar patterns. Fix each with the existing batch repository methods where possible.
    - Why: Each round-trip to the database adds latency. With async SQLAlchemy, these could also be `asyncio.gather()`'d, but batching at the query level is simpler and more portable.

### v1.0.2: Database Migration (conditional)
**Goal**: If v1.0.0 recommends it, migrate to PostgreSQL or normalized tag storage — whichever the investigation favors.
**Context**: This version only executes if the v1.0.0 evaluation recommends a structural change. At the app's current scale, v1.0.1 optimizations may be sufficient indefinitely. But if the couple wants remote access, multi-device sync, or the benchmark data shows SQLite JSON limitations at projected scale, this is the path forward.
**What this unlocks**: Depends on the chosen path. PostgreSQL: remote deployment, concurrent access, JSONB+GIN for tag queries. Normalized tables: tag management features (rename, merge, usage stats), portable across databases.
**Key tech choices**: Determined by v1.0.0 investigation. Two possible paths documented below — only one will be executed.

#### Path A: PostgreSQL Migration

- [ ] **PostgreSQL infrastructure**
    - Effort: M
    - Dependencies: v1.0.1
    - What: Replace `sqlite+aiosqlite` with `postgresql+asyncpg` in the database connection layer. Add connection pooling configuration. Update `settings.py` with PostgreSQL connection parameters. Verify all SQLAlchemy models and queries are dialect-agnostic (or add dialect-specific branches). Set up a local PostgreSQL instance for development (Docker Compose or native).
    - Why: Foundation for all PostgreSQL-specific optimizations.
    - Notes:
        - `asyncpg` is the standard async PostgreSQL driver for Python in 2026
        - Connection pooling matters for PostgreSQL (unlike SQLite); configure `pool_size`, `pool_pre_ping`
        - SQLAlchemy 2.0+ handles most dialect differences, but `json_each()` raw SQL will need PostgreSQL equivalents

- [ ] **JSONB tag column + GIN index**
    - Effort: S
    - Dependencies: "PostgreSQL infrastructure"
    - What: Alembic migration: change `tags_json String` to `tags JSONB`. Add GIN index: `CREATE INDEX ix_transactions_tags_gin ON transactions USING GIN (tags)`. Update repository serialization to use native JSONB (no more `json.dumps`/`json.loads`). Tag containment queries become `WHERE tags @> '["shared"]'` — indexed, O(log n).
    - Why: This is the gold-standard solution for "array of strings" queries in PostgreSQL. GIN indexes make element membership checks fast regardless of array size or row count.

- [ ] **Alembic data migration**
    - Effort: M
    - Dependencies: "PostgreSQL infrastructure"
    - What: Migration script that transfers data from SQLite to PostgreSQL. Export SQLite data, transform column types (String → JSONB for tags, datetime strings → timestamps), import into PostgreSQL. Verify row counts and data integrity post-migration. Provide a rollback path (keep SQLite as read-only backup).
    - Why: Zero-downtime data migration for the couple's existing transaction history.

#### Path B: Normalized Tag Storage

- [ ] **Tag normalization schema**
    - Effort: M
    - Dependencies: v1.0.1
    - What: New tables: `tags` (id, name UNIQUE) and `transaction_tags` (transaction_id FK, tag_id FK, PK). Alembic migration that creates the tables, populates from existing `tags_json`, and keeps `tags_json` temporarily for rollback safety. Composite index on `(tag_id, transaction_id)` for "all transactions with tag X" queries. Follow-up migration drops `tags_json` after verification.
    - Why: Standard relational pattern. Works on any database. Enables features that JSON storage can't: tag rename (one row update), tag merge, orphan cleanup, usage statistics.

- [ ] **Repository + use case updates**
    - Effort: M
    - Dependencies: "Tag normalization schema"
    - What: `TransactionRepository._to_domain()` assembles `tags: tuple[str, ...]` from `selectinload` relationship. `get_distinct_tags()` becomes `SELECT DISTINCT name FROM tags`. `BulkModifyTagsUseCase` changes from evolving a tuple to inserting/deleting junction rows. Domain layer (`Transaction` entity, CSV parsing) is unaffected — it still works with `tuple[str, ...]`.
    - Why: Infrastructure adapts to the new schema while domain stays pure.

- [ ] **Tag management features**
    - Effort: S
    - Dependencies: "Repository + use case updates"
    - What: With normalized storage, add: tag rename (update one `tags` row → all transactions updated), tag merge (reassign junction rows, delete source tag), and tag usage counts (simple aggregation on `transaction_tags`). New use cases + API endpoints. Optional — only if the couple finds tag management valuable.
    - Why: Free features enabled by normalization that aren't possible with JSON storage.

### v1.0.3: Production Readiness (conditional)
**Goal**: Deployment infrastructure and operational concerns for running the app beyond localhost.
**Context**: The app currently runs as a local dev server. If the couple wants remote access (check settlement status from their phones) or shared hosting, these items make the app production-viable.
**What this unlocks**: Remote access, data safety, and operational visibility.

#### Deployment

- [ ] **Docker containerization**
    - Effort: M
    - Dependencies: v1.0.2 (if PostgreSQL) or v1.0.1 (if staying SQLite)
    - What: `Dockerfile` for the FastAPI backend (multi-stage build, minimal image). `docker-compose.yml` with backend + frontend (Vite build served by nginx or backend static files) + database (PostgreSQL container if applicable, or SQLite volume mount). Health check endpoint (`GET /api/v1/health`). Environment variable configuration for database URL, port, and debug mode.
    - Why: Reproducible deployment, easy to run on a home server or cheap VPS.

#### Data Safety

- [ ] **Automated backups**
    - Effort: S
    - Dependencies: "Docker containerization"
    - What: For SQLite: scheduled `sqlite3 .backup` to a timestamped file, with configurable retention (e.g., keep 30 daily backups). For PostgreSQL: `pg_dump` equivalent. Backup script runnable via cron or Docker health check sidecar. Restore documentation.
    - Why: The couple's financial data is irreplaceable. Backups should be automatic, not manual.

#### Observability

- [ ] **Structured logging + health check**
    - Effort: S
    - Dependencies: v1.0.1
    - What: Review loguru configuration for structured JSON output (useful when running in Docker). Add `GET /api/v1/health` endpoint that checks database connectivity and returns app version. Add request timing middleware (log slow queries > 100ms).
    - Why: Operational basics for knowing the app is healthy and diagnosing issues.
