### v1.0.0: PostgreSQL Migration
**Goal**: Migrate from SQLite to PostgreSQL 18 on Neon — swap the driver, migrate the schema and data, and take advantage of JSONB+GIN for tag storage.
**Status**: Completed (2026-03-27)
**Context**: The app runs locally on each person's laptop and connects to Neon over the network. Neon handles hosting, connection pooling, backups (point-in-time recovery), and branching. No self-hosted infrastructure needed. SQLAlchemy 2.0+ handles most dialect differences, but SQLite-specific raw SQL (e.g., `json_each()`) needs PostgreSQL equivalents.
**What this unlocks**: Multi-device access (check settlement from your phone), JSONB+GIN for O(log n) tag queries, concurrent access without SQLite's write lock, and a foundation for server-side tag filtering.

### v1.0.1: Multi-User Readiness
**Goal**: Harden the app for two people using it simultaneously against the same Neon database, and optimize indexes for PostgreSQL.
**Status**: Completed (2026-03-28)
**Context**: With both partners connecting to Neon from separate laptops, the together session is the critical concurrent window. Data freshness and index coverage need attention before real multi-user usage. Neon LISTEN/NOTIFY is a poor fit (incompatible with connection pooler, killed by scale-to-zero, no message guarantees). Smart polling is proportional; SSE is the upgrade path if needed.
**What this unlocks**: Confident two-person usage — both partners see each other's changes within seconds, and queries are properly indexed for PostgreSQL.

#### Multi-User Hardening

- [x] **Smart polling for together-session pages**
    - Effort: S
    - Dependencies: v1.0.0
    - Status: Completed (2026-03-28)
    - What: Added `refetchInterval: 5_000` to TanStack Query hooks on Dashboard, Settle Up, and Transactions pages. Audited existing `staleTime` (30s) and `refetchOnWindowFocus` (true) — both complementary, no changes needed. Scoped to together-session pages only (not Upload/Settings/Insights).
    - Why: The together session is the one time both people use the app simultaneously. Without polling, one person records a payment or locks the month and the other sees stale data until manual refresh.

- [x] **SSE event bus for instant cross-user sync**
    - Effort: M
    - Dependencies: "Smart polling for together-session pages"
    - Status: Completed (2026-03-28)
    - What: Added `GET /api/v1/events` SSE endpoint using FastAPI's built-in `EventSourceResponse` + `ServerSentEvent` with an in-memory `asyncio.Queue` per connected client. After any mutation (upload, settlement, finalization, transaction edit), broadcasts the affected entity name (e.g., `{"entity": "settlements"}`). Frontend `useRealtimeSync` hook opens an `EventSource` connection and calls `queryClient.invalidateQueries()` on received events. `EventSource` provides auto-reconnection for free. Works with existing httpOnly cookie auth. Smart polling remains as fallback.
    - Why: Upgrades from 5-second polling to sub-second updates. The in-memory event bus is proportional — no Redis, no message broker, no persistent connections to Neon. If one user is offline when an event fires, they get fresh data on next page load via normal TanStack Query mechanics.
    - Notes:
        - Skip WebSockets — no bidirectional communication needed, SSE is simpler and auto-reconnects
        - Skip Neon LISTEN/NOTIFY — incompatible with connection pooling, killed by scale-to-zero, no delivery guarantees
        - In-memory queue means events are lost on server restart — acceptable for a local dev server with 2 users

#### Index Optimization

- [x] **PostgreSQL index audit**
    - Effort: S
    - Dependencies: v1.0.0
    - Status: Completed (2026-03-28)
    - What: Audited all indexes against query patterns. Added two high-impact indexes via Alembic migration 0002: (1) partial index `ix_transactions_non_settlement_date` on `(household, date) WHERE NOT is_settlement` — covers 4 repository methods that filter non-settlement transactions; (2) `ix_settlements_year_month` on `(year, month)` — covers period lookups. Skipped low-cardinality tables (persons, categories, reconciliation_periods, budgets).
    - Why: Indexes are the highest-leverage, lowest-risk performance improvement. A systematic audit prevents ad-hoc index additions.

### v1.0.2: Query Optimization
**Goal**: Ship PostgreSQL-native query improvements now that JSONB+GIN is available.
**Context**: v1.0.0 established the PostgreSQL foundation. This version exploits PostgreSQL capabilities for tag queries and server-side filtering that weren't possible with SQLite's JSON support.
**What this unlocks**: Server-side tag filtering, faster tag queries, and reduced client-side data processing.

#### Tag Queries

- [x] **`get_distinct_tags()` via JSONB**
    - Effort: S
    - Dependencies: v1.0.0
    - Status: Completed (2026-03-27) — done as part of v1.0.0
    - What: Replaced Python-side `json.loads()` loop with `SELECT DISTINCT jsonb_array_elements_text(tags)`.

- [ ] **Server-side tag filtering**
    - Effort: M
    - Dependencies: "`get_distinct_tags()` via JSONB"
    - What: Add optional `tags` query parameter to the transactions/reconciliation endpoint. SQL filter: `WHERE tags @> :tag_array` using the GIN index. The frontend `useTransactionFilters` hook stays client-side for instant interaction, but the initial data fetch can be scoped by tag when the user navigates with a tag pre-selected (e.g., deep-linking from a tag chip).
    - Why: Reduces payload size when filtering by tag. Foundation for future tag-based views.

#### Query Patterns

- [ ] **Sequential query batching**
    - Effort: S
    - Dependencies: v1.0.0
    - What: Review and batch sequential database calls identified during development. Known candidates: `validate_settlement_persons()` makes two sequential `get_by_id()` calls that could be a single `get_by_ids()`. Audit all use cases for similar patterns. Fix each with the existing batch repository methods where possible.
    - Why: Each round-trip to Neon has network latency (unlike local SQLite). Batching queries is more impactful with a remote database.
