# v1.7.x: Financial Accuracy

For strategic overview, see the [planning overview](README.md).

## Why this version

A whole-project financial-accuracy review (2026-07-02) — ten independent review angles, every candidate adversarially verified, many by executing the domain functions directly — confirmed roughly forty defects. Five of them are "the money is wrong" classes:

1. **Waiving a balance does nothing** — waivers persist `amount=0` and no consumer special-cases `is_waived`, so the balance, warnings, and settled status never change.
2. **Re-upload double-counts** — re-upload is an upsert-merge; rows that changed or were deleted in Monarch leave stale twins that keep counting.
3. **Spotted debts never reach Settle Up** — the parser stores person-name tags as `household=false` while every settlement fetch filters `household=true`; the Transactions page *does* include them (for the payer-viewer only), so two pages disagree about who owes whom.
4. **Refunds inflate budgets** — budget and dashboard aggregations `abs()`-add positive amounts as spending, while reconcile/insights net or exclude them.
5. **Re-upload silently unlinks settlements** — accepting an innocuous "merchant changed" diff resets in-app `is_settlement`/`is_excluded` flags without showing it in the preview.

Beyond those: cross-page disagreements (three different YTD numbers, two "household spending" figures on one dashboard), a copy-budgets flow that has never rendered in production, and a recurring pattern of **tests masked by fixtures that produce states production cannot produce**. This epic burns the list down in severity order. Follow-ups scoped to the uncommitted v1.6.0 diff shipped as [v1.6.1](completed/v1.6.x.md).

The epic closes with a thesis correction (v1.7.5): the original one-complete-reconciliation-per-month model doesn't match how the couple actually settles — partial rent payments on the 1st, skipped months, and multi-month catch-ups. That version remodels settlement as a running ledger.

## Suggested execution pattern

Validated on v1.7.0 (orchestrator implemented directly) and v1.7.1 (delegated): the orchestrating agent — running on the strongest available model — explores the current code, writes a **self-contained handoff brief** (spec pointer, verified current-state facts with file/line refs, ordered per-item commit plan, test plan, quality gates, commit/backlog conventions, known gotchas), then farms implementation out to a fresh-context agent sized to the work, preserving its own context for review. On completion the orchestrator verifies independently — `git log`, full backend + frontend quality gates, a user-story validation walk — rather than trusting the agent's report. Keep the brief on disk (`~/.claude/plans/`) so a stalled agent or fresh session can resume from it. Each version below carries a **Delegation** line sizing the implementation agent (model class + thinking level); when in doubt, size up for anything touching settlement math or migrations.

### v1.7.1: Upload & Re-upload Integrity

**Status**: Completed (2026-07-03)

Upload deletes them; settlement links on deleted rows are unlinked with a warning surfaced in the result; the preview shows the removed count alongside new/changed/unchanged so nothing disappears silently. Tests assert replacement (none currently do).
    - Files: `src/application/use_cases/upload_csv.py`, `src/application/use_cases/preview_csv.py`, `src/application/use_cases/_shared/transactions.py`, `src/domain/dedup.py`, `src/infrastructure/persistence/repositories/transaction_repository.py`, `web/src/pages/UploadPage.tsx`, `tests/unit/application/test_upload_csv.py`

- [x] **Preserve in-app flags on accepted "changed" rows**
    - Effort: S
    - What: `is_settlement`/`is_excluded` are set in-app (link, exclude) but absent from `_MUTABLE_FIELDS`, while `update_mutable_fields_batch` writes them from the freshly parsed row — so accepting a merchant rename silently re-admits a linked transfer to spending. Carry the existing flag values through the update (or exclude the columns from the write set). Test: linked transfer survives a re-upload with a changed merchant.
    - Files: `src/infrastructure/persistence/repositories/transaction_repository.py`, `src/application/use_cases/upload_csv.py`, `tests/unit/application/test_upload_csv.py`

- [x] **Parser hardening: non-finite amounts and truncated rows**

### v1.7.5: Settlement Ledger — Reconciliation Across Months
**Goal**: Represent how the couple actually settles — partial rent payments monthly, skipped months, and one catch-up payment covering 3+ months — with a single running outstanding balance.
**Status**: Planned
**Context**: The original thesis assumed one complete reconciliation per month. In practice the couple is inconsistent: they always partially settle to cover rent on the 1st, sometimes miss the full reconciliation for a month or two, then clear everything with one big catch-up. The current model binds every settlement to exactly one `(year, month)` and nets each month in isolation — a multi-month catch-up **cannot be represented** (and the settlement-link unique index means the single catch-up Venmo transfer can back only one month's settlement), and no surface shows the total outstanding across months. Multiple settlements per month, partial amounts, and paying after the month already work today and just need pinning tests. **Depends on v1.7.0** — build the ledger on corrected settlement math (scope, direction, waivers).
**What this unlocks**: The hero answers the couple's actual question ("what do we still owe each other, in total?"), catch-up payments become first-class, and month history reads honestly for skipped months.

## Decisions

Six product decisions are embedded in this epic. All six were reviewed and confirmed one-by-one on 2026-07-02 (five by the user directly; the ledger model by user-requested research review). They are settled — implement as written.

**Settlement ignores `household` (v1.7.0). — CONFIRMED by user 2026-07-02.** Any `payer_percentage < 100` transaction enters settlement math, full stop. The user's definition, verbatim in spirit: household = something we did together, regardless of who paid; personal = not household, where I pay for myself; spotted = personal where one partner paid for the other — so a spotted expense is the *beneficiary's* personal spending ("if Bob pays for Alice and it's not household, then it's Alice's personal"). Whether it's household doesn't matter for settlement: if Bob pays for Alice — personal or household — Alice pays it back. Spotted stays `household=false`, is excluded from the household budget (US-REVIEW-5's "a debt"), and attributes to the beneficiary's personal spending (see v1.7.2). domain.md's tag table is corrected to match. The alternative — person-name tags setting `household=true` — was rejected: it keeps settlement coupled to the budget flag and counts one partner's expense as couple spending.

**Re-upload is a true replace (v1.7.1). — CONFIRMED by user 2026-07-02.** US-IMPORT-1 says "replaced"; merge semantics created an entire class of double-counting. Deletion is scoped to the uploader's rows within the upload's date window, previewed as a "removed" count, and unlinks settlements with a warning rather than silently. Confirmed safe because the couple's Monarch exports are always complete for their date range — never filtered or single-account.

**Waivers persist the remaining balance as their amount (v1.7.0). — CONFIRMED by user 2026-07-02.** No `is_waived` special-casing in the math — `compute_net_position` stays one rule, and payment history reads "waived $50" instead of "waived $0". If the balance changes after a waive (late edit), the difference resurfaces — correct; Lock Month is the freeze. Add a warning when waiving while an upload is missing.

**Refunds net everywhere (v1.7.2). — CONFIRMED by user 2026-07-02.** Every spending aggregation becomes sign-aware, matching `reconcile()`'s `total_spending − total_refunds`. A returned purchase reduces spending; it never inflates it. Cross-month returns may produce a negative category month — render it as-is, don't clamp.

**Settlement is a running ledger, not per-month math (v1.7.5). — CONFIRMED by research review 2026-07-02.** Outstanding balance = all-time gross − all-time payments; settlements carry no *binding* month (an optional "recorded against" annotation remains for human labels like "April rent" — display only, never math); per-month status is derived FIFO oldest-first. This is **balance-forward accounting**, the formally documented method for parties who pay regularly (vs. open-item, the B2B pattern requiring payment-to-invoice matching): see [Oracle's open-item vs balance-forward definition](https://docs.oracle.com/en/industries/energy-water/ccb/29013/ccb-user-guides/Topics/C1_03Finan_Open_Item_Versus_Balance_Forward_.html) — "payments implicitly relieve a customer's oldest debt" is FIFO verbatim. Every consumer splitting app uses this model (Splitwise settle-up prefills the total and accepts any partial amount against the running balance; Tricount shows one balance overview per pair), and QuickBooks' own default applies payments to the oldest open invoice first. Explicit allocation was rejected: it's the open-item pattern, whose payoff (invoice-level audit) doesn't exist between two people, at the cost of an allocation step on every payment. Known display fiction: a rent payment may show as covering an older month's leftovers; the annotation is the mitigation.

**The hero shows total outstanding (v1.7.5). — CONFIRMED by user 2026-07-02.** Dashboard settlement card and Settle Up hero show the cumulative balance with its covered span ("Kew owes Ash $842 · covers Mar–May"); months become drill-downs with their gross, derived status, and the month-scoped audit table. A month-scoped hero understates reality whenever a month was skipped — exactly the case that motivated the version. Together-session flow: settle the total in one payment, then lock months individually from the drill-down (Lock Month stays month-scoped). Matches the peer-app convention: Splitwise/Tricount/Settle Up all lead with the single pair balance.
