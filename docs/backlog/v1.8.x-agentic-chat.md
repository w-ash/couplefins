# v1.8.x — Agentic Chat (Series Overview)

The v1.8.x series upgrades the chat assistant from a narrow 9-tool Q&A bot
into a full agentic interface to the app, governed by one product principle:

> **Anything a human can do through the app, the chatbot can do for them —
> and nothing more.** The only exceptions are an explicit human-only
> blacklist: authentication (login/logout, all password flows), couple setup,
> and person preferences (theme, chat voice, adjustment account). CSV upload
> is excluded mechanically (chat has no file input), not by policy.

The contract is enforced in code, not convention:
`src/application/chat/registry.py` classifies every use case in
`src/application/use_cases/`, and
`tests/unit/application/chat/test_registry_parity.py` fails CI whenever a use
case is unclassified, a blacklisted use case becomes chat-reachable, or a
classification goes stale. Mutations are never applied directly — every write
tool proposes a change that the human confirms via a confirmation card
(two-phase `PendingActionStore` flow), which is the deterministic layer of the
prompt-injection defense: untrusted content in the data (merchant names,
notes, tags) can at worst propose, never execute. Layered on top of it,
per current Anthropic guidance: untrusted content reaches the model only
inside JSON-encoded `tool_result` blocks (the JSON escaping is the primary
delimiting — attackers can't break out of the data context), and
user-originated strings additionally carry `<user_data>` source labels
(today only merchant names are labeled; v1.8.1 extends the labeling to every
user-originated field).

## Design grounding (July 2026)

- [Anthropic: Effective context engineering](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)
  (Sep 2025) — smallest high-signal token set; subagents = clean context
  windows returning condensed summaries (~1–2K tokens).
- [Anthropic: Writing effective tools for agents](https://www.anthropic.com/engineering/writing-tools-for-agents)
  (Sep 2025) — consolidate rather than wrap endpoints 1:1 (hence
  `get_settlement_activity` covering three use cases); human-readable fields;
  pagination/truncation defaults; prescriptive "call this when…" descriptions.
- [Anthropic: Advanced tool use](https://www.anthropic.com/engineering/advanced-tool-use)
  (Nov 2025) — tool search / `defer_loading` recommended at **10+ tools**
  (measured accuracy gain, not just token savings); programmatic tool calling
  for 3+ dependent calls or large-result aggregation; `input_examples` for
  parameters a schema can't fully express.
- [Anthropic: Code execution with MCP](https://www.anthropic.com/engineering/code-execution-with-mcp)
  (Nov 2025) — filter and aggregate tool results inside the sandbox so only
  the answer enters model context.
- [Context editing docs](https://platform.claude.com/docs/en/build-with-claude/context-editing)
  — `clear_tool_uses_20250919` (beta) for tool-result clearing; server-side
  `compact_20260112` (Jan 2026) now preferred over client-side compaction,
  which is deprecated.
- Opus 4.8 migration guidance — adaptive thinking must be explicit; the model
  under-reaches for subagents/custom tools unless each description states its
  trigger; effort is the primary cost/quality knob (current effort docs
  recommend `xhigh` for a main agent loop and `low` for subagents — verify
  exact enum values at implementation).
- Prompt-injection guidance (2026) — the untrusted-content → state-mutation
  chain is the dominant threat. Current stack per
  [Anthropic's mitigation docs](https://platform.claude.com/docs/en/test-and-evaluate/strengthen-guardrails/mitigate-jailbreaks):
  untrusted content only in `tool_result` blocks, JSON-encoded, with source
  labels, plus a system-prompt policy that instructions found in retrieved
  content are data to report, not commands to follow. Prompting-only defenses
  are model-dependent and insufficient alone (arXiv 2606.18530, Jun 2026);
  deterministic layers are what hold
  ([How we contain Claude](https://www.anthropic.com/engineering/how-we-contain-claude),
  May 2026) — here that layer is mutations-as-proposals. The same source
  documents approval fatigue (~93% of permission prompts get approved), so
  confirmation cards must show concrete before/after details, never just an
  action name.

## Standing conventions for this series

- New tool = schema in `tools.py` + handler in `tool_executor.py`
  (+ executor in `confirmed_actions.py` for writes) + `ToolSpec` in
  `registry.py` + parity bookkeeping + tests. The registry shape test
  enforces executor/broadcast on writes.
- Tool descriptions lead with a trigger sentence; mutation descriptions state
  that they propose, never apply.
- List-returning tools cap at ~20 rows with `total_count`; all
  user-originated strings carry `<user_data>` source labels (on top of the
  JSON encoding every tool result already gets). Schemas do NOT set
  `strict: true` — tried in v1.8.1/v1.8.2, abandoned against live API
  limits (20-strict-tool cap, compiled-grammar size cap, no numeric/array
  constraints); handler validation is the boundary. Schemas keep
  `additionalProperties: false` and prose ranges.
- Frontend: generic result/confirmation cards are the default renderers;
  bespoke cards only for high-traffic tools.
- Every phase ends with the full quality gate
  (`uv run ruff check . --fix && uv run ruff format . && uv run basedpyright src/ && uv run vulture && uv run pytest`
  + `pnpm check && pnpm test`) and a live chat smoke test.
