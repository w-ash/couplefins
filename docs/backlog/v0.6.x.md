### v0.6.0: Settlement Page, Recording & Bulk Editing
**Goal**: Give settlement its own dedicated page, let the couple record/waive payments, and provide bulk editing tools for transaction categories, tags, and splits.
**Context**: Settlement is the core "together moment" — the reason the couple opens the app side by side. Previously the settlement card was duplicated on Dashboard and Transactions pages, and finalization controls were embedded in the Transactions page. Settlement deserves a focused experience. Separately, editing transactions one-at-a-time was slow for common operations like re-categorizing or re-tagging multiple transactions.
**What this unlocks**: Clear separation between solo prep (Transactions), overview (Dashboard), and the together session (Settlement). Completing the core loop — upload → reconcile → settle → finalize becomes a tracked end-to-end workflow on a dedicated page. Bulk editing makes solo prep dramatically faster.
**Key tech choices**: New `/settle` route with month selector (settlement is inherently monthly). `Settlement` entity with payment method enum and `is_waived` flag. `SettlementTransactionLink` junction entity to associate transactions with settlement records. `GetSettleUpData` composite use case aggregates owed amount, recorded settlements, remaining balance, upload statuses, and finalization state. `BulkUpdateTransactionsUseCase` replaces the single-item `UpdateTransactionUseCase`. Shared `transaction_pipeline` helpers (fetch/validate/edit) eliminate duplication across bulk use cases.

#### Settlement Use Cases

- [x] **RecordSettlementUseCase**
    - Effort: M
    - Status: Completed (2026-03-15)
    - Dependencies: "Settlement persistence layer"
    - What: Creates a settlement record with amount, method, notes, and optional linked transaction IDs. Validates persons exist and differ. If linked transactions provided, creates `SettlementTransactionLink` entries and marks transactions with `is_settlement=True`.
    - Why: Core backend logic for recording a payment
    - Notes:
        - Recording is not finalization-guarded — paying a debt is documenting reality
        - Uses shared `validate_settlement_persons()` from `_shared/settlement_records.py`

- [x] **RecordWaivedSettlementUseCase**
    - Effort: S
    - Status: Completed (2026-03-15)
    - Dependencies: "Settlement persistence layer"
    - What: Creates a settlement with `amount=0` and `is_waived=True`. No linked transactions. Validates persons.
    - Why: Sometimes the couple agrees to forgive a balance rather than pay it

- [x] **GetSettleUpDataUseCase**
    - Effort: M
    - Status: Completed (2026-03-15)
    - Dependencies: "Settlement persistence layer"
    - What: Composite use case that aggregates everything the Settle Up page needs in one query: owed amount (from reconciliation engine), recorded settlements (enriched with linked transaction IDs), remaining balance, upload statuses, persons, and finalization state.
    - Why: Single endpoint for the settle-up page — avoids multiple round-trips
    - Notes:
        - `remaining_balance = max(0, owed - total_settled)`
        - Uses `enrich_with_links()` from `_shared/settlement_records.py` to attach transaction links

- [x] **GetSettlementsUseCase**
    - Effort: S
    - Status: Completed (2026-03-15)

- [x] **DeleteSettlementUseCase**
    - Effort: S
    - Status: Completed (2026-03-15)
    - Dependencies: "Settlement persistence layer"
    - What: Deletes a settlement record and its transaction links. Guarded by finalization.

- [x] **MarkTransactionAsSettlementUseCase**
    - Effort: S
    - Status: Completed (2026-03-15)

    - What: Toggles `is_settlement` flag on a transaction. Optionally creates a `SettlementTransactionLink` to associate it with a specific settlement.

#### Bulk Transaction Editing

- [x] **BulkUpdateTransactionsUseCase (replaces UpdateTransactionUseCase)**
    - Effort: M
    - Status: Completed (2026-03-15)
    - Dependencies: v0.5.5
    - What: `PATCH /api/v1/transactions/bulk-update` — update category, tags, or payer_percentage on multiple transactions. Also supports date/amount on single transactions (preserves `original_date`/`original_amount`). Creates `TransactionEdit` audit entries. Replaces the single-item `UpdateTransactionUseCase` (deleted).
    - Why: Bulk operations are the common case — editing 10 miscategorized transactions one at a time was painful
    - Notes:
        - date/amount restricted to single-item updates (immutable field safety)
        - Uses `fetch_and_validate()` for batch loading + finalization guard
        - Uses `compute_edit()` for audit trail
        - PATCH semantics: `None` = unchanged, `_UNSET` sentinel for payer_percentage

- [x] **BulkModifyTagsUseCase**
    - Effort: S
    - Status: Completed (2026-03-15)
    - Dependencies: v0.5.5
    - What: `POST /api/v1/transactions/bulk-tags` — add or remove tags in bulk via `TagAction` enum (ADD/REMOVE). Creates `TransactionEdit` audit entries. Preserves tag ordering.
    - Why: Tagging multiple transactions (e.g., adding "vacation" to 15 restaurant charges) was tedious
    - Notes:
        - Add: appends new tags, preserves order, deduplicates
        - Remove: filters out specified tags

- [x] **GetTagsUseCase**
    - Effort: S
    - Status: Completed (2026-03-15)
    - Dependencies: v0.5.5
    - What: `GET /api/v1/tags` — fetch all distinct tags across transactions.
    - Why: Powers tag dropdowns and comboboxes in bulk editing UI

- [x] **BulkEditToolbar component**
    - Effort: M
    - Status: Completed (2026-03-15)
    - Dependencies: "BulkUpdateTransactionsUseCase", "BulkModifyTagsUseCase", "GetTagsUseCase"
    - What: Tab-based toolbar with three panels: Split (percentage input), Category (searchable combobox), Tags (add/remove toggle + multi-select combobox with tag count indicators). Shows selected count. Apply/Cancel flow with loading states. Replaces the simpler `BulkSplitEditor` from v0.5.0.
