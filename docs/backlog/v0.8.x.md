# v0.8.x: Upload Polish & Data Quality

For strategic overview, see the [planning overview](README.md).

**Research basis**: Before designing this version series, we reviewed upload UX patterns across Uploadcare, Filestack, Flatfile, OneSchema, and ImportCSV. We also studied mobile file upload patterns, CSV import UX anti-patterns, and accessibility guidelines (WCAG 2.5.8 target size, ARIA drag-and-drop). Key findings that shaped every decision below:

- **Responsive layout first** — the upload page is the only page with a hard-coded two-column grid (`grid-cols-[1fr_16rem]`). Building drag-and-drop into a broken mobile layout means rework. Fix the container, then fill it.
- **Drop zones need four visual states** — idle, drag-over, file-selected, disabled. Users need feedback at every interaction point, not just after the drop. Counter-based `dragenter`/`dragleave` tracking avoids false state changes from nested elements.
- **Touch targets minimum 44px** — per WCAG 2.5.8 and Apple HIG. The current file input and select are ~32px (`py-2`).
- **Catch errors before the round-trip** — wrong file type, empty file, wrong CSV format are the cheapest errors to catch client-side. Server-side, batch all row errors instead of failing on the first one — the "fix one, reupload, find the next" loop is the #1 CSV import frustration.
- **Upload history answers a real question** — "When did we last upload?" and "What was in that upload?" come up every month during solo prep. The data already exists in the `uploads` table — surface it.
- **Post-upload is a decision point** — "Upload Complete" with a bare "Upload Another CSV" button leaves the user to figure out what to do next. Contextual next-step links guide the solo prep workflow.

### v0.8.0: Responsive Upload Layout
**Goal**: Make the upload page work on any screen size, from phone to desktop.
**Context**: The upload page uses `grid-cols-[1fr_16rem]` — a fixed two-column layout where the action panel is a 16rem sticky sidebar. On screens narrower than ~700px this either overflows or crushes the content column. Zero responsive breakpoints exist (no `sm:`, `md:`, `lg:` classes). Every other page uses a single-column `mx-auto max-w-Xll px-6 py-12` container that naturally adapts. The upload page is the outlier.
**What this unlocks**: Usable uploads from any device. Foundation for drag-and-drop and upload history to be built responsive from the start. v0.9.0 can skip the upload page — it's already handled.

#### Layout

- [x] **Responsive two-column grid**
    - Effort: S
    - Dependencies: v0.7.2
    - What: Replace `grid-cols-[1fr_16rem]` in `UploadPage.tsx` with `grid-cols-1 md:grid-cols-[1fr_16rem]`. Below `md:`, the action panel renders inline below preview/review content instead of as a sticky sidebar. The `sticky top-6 self-start` classes become `md:sticky md:top-6 md:self-start`. The `showGrid` conditional max-width becomes `max-w-3xl md:max-w-5xl`.
    - Why: Single change that makes the page functional at any width

- [x] **Mobile preview card layout**
    - Effort: S
    - Dependencies: "Responsive two-column grid"
    - What: The preview table has 6 columns (Date, Merchant, Category, Amount, Type, Split). Below `sm:`, switch to a card layout — one card per transaction with key fields stacked vertically. Table layout preserved above `sm:`. The preview only shows `PREVIEW_LIMIT = 5` rows, so cards are feasible without virtual scrolling.
    - Why: 6-column tables are unusable on 320px screens

- [x] **Touch-friendly form controls**
    - Effort: XS
    - Dependencies: none
    - What: Add `min-h-11` (44px) to the file `<input>` and person `<select>`. These are the minimum recommended touch targets per WCAG 2.5.8. The "Preview CSV" button already meets this via the `Button` component's default sizing.
    - Why: Touch targets below 44px cause tap errors on phones

- [x] **Review card diff wrapping**
    - Effort: XS
    - Dependencies: none
    - What: The diff display (`flex gap-2` with old → arrow → new values) can overflow on narrow screens when values are long (e.g., "Coffee Shops & Treats → Food & Dining"). Add `flex-wrap` to the diff row.
    - Why: Prevents horizontal overflow of long category names on small screens

### v0.8.1: Drag-and-Drop File Zone
**Goal**: Replace the bare file input with a drag-and-drop zone that provides clear visual feedback at every interaction state.
**Context**: The current `<input type="file" accept=".csv">` works but is the bare minimum. Drag-and-drop is a standard UX expectation for file upload. With v0.8.0's responsive layout in place, this component is built mobile-aware from the start — the drop zone is a touch-to-browse zone on phones, a drag target on desktop.
**What this unlocks**: Faster file selection, clearer visual state communication, and the hook point for client-side validation in v0.8.3.

#### Component

- [ ] **FileDropZone component**
    - Effort: S
    - Dependencies: v0.8.0
    - What: New `web/src/components/FileDropZone.tsx`. A controlled component wrapping drag-and-drop + an internal hidden `<input type="file">`. Props: `accept`, `onFile`, `disabled`, `currentFile`. Four visual states:
        1. **Idle**: Dashed border (`border-dashed border-2 border-border`), centered upload icon + "Drop your CSV here, or click to browse". Rounded corners matching `Card` (`rounded-xl`).
        2. **Drag-over**: Border shifts to `border-primary`, background becomes `bg-accent`, icon subtly scales. Counter-based `dragenter`/`dragleave` tracking handles nested elements.
        3. **File selected**: Solid border (`border-solid border-input`), shows file name + size + "Change file" link.
        4. **Disabled**: `opacity-50 cursor-not-allowed`, drag events ignored.
    - Why: Encapsulated, testable component with unambiguous feedback at every state
    - Notes:
        - Component is a `<label>` wrapping the hidden `<input>`. `tabIndex={0}`, keyboard activation via Enter/Space. `aria-describedby` pointing to help text.
        - Mobile browsers ignore drag events and show native file picker on tap — correct behavior, click-to-browse fallback handles it.
        - Rejects non-`.csv` files on drop with inline error.

- [ ] **Integrate into UploadPage**
    - Effort: XS
    - Dependencies: "FileDropZone component"
    - What: Replace the current file `<input>` section with `<FileDropZone>`. The `onFile` callback stores the `File` in `useState<File | null>`. `buildFormData()` reads from this state instead of `fileInputRef.current.files[0]`. Remove the `fileInputRef`. `handleReset` clears the file state. `isFormDisabled` passes through to `FileDropZone.disabled`.
    - Why: Swaps the implementation without changing data flow or API calls

- [ ] **FileDropZone tests**
    - Effort: S
    - Dependencies: "FileDropZone component"
    - What: `web/src/components/FileDropZone.test.tsx`. All four states: idle renders, drag-over applies active styling (`fireEvent.dragEnter`), file selection via click calls `onFile`, file selected shows name and size, disabled prevents interaction. Non-CSV file rejection (drop a `.txt`, verify error). Use `@testing-library/react` with `fireEvent.drop`.
    - Why: Drag-and-drop event handling is easy to break with regressions

### v0.8.2: Upload History
**Goal**: Show past uploads so the couple can answer "when did we last upload?" and "what was in each upload?"
**Context**: The `Upload` entity stores `id`, `person_id`, `filename`, `uploaded_at` — but nowhere in the UI surfaces this data. The monthly solo-prep workflow involves uploading on separate days. Knowing whether your partner has uploaded and what their upload contained is currently limited to a has/hasn't indicator on the Dashboard.
**What this unlocks**: Upload audit trail, debugging ("did I re-upload this month?"), and confidence in the data pipeline.

#### Backend

- [ ] **Upload history result type**
    - Effort: XS
    - Dependencies: v0.8.1
    - What: New `UploadHistoryEntry` (frozen attrs) in the use case result — not a domain entity change. Fields: `upload_id`, `person_id`, `person_name`, `filename`, `uploaded_at`, `transaction_count`, `shared_count`, `date_range_start: date | None`, `date_range_end: date | None`. Keeps the Upload entity pure and minimal — enrichment happens at the use case layer.
    - Why: Transaction counts are derived data. Storing them on the entity creates cache-invalidation problems when transactions are edited or re-uploaded.

- [ ] **Upload history repository method**
    - Effort: S
    - Dependencies: "Upload history result type"
    - What: Add `get_all_with_transaction_counts()` to `UploadRepository` — single SQL query joining `uploads` with `transactions`, grouping by `upload_id` to get `COUNT(*)`, `SUM(CASE WHEN is_shared THEN 1 ELSE 0 END)`, `MIN(date)`, `MAX(date)`. Add Protocol method to `UploadRepositoryProtocol`. Returns results ordered by `uploaded_at DESC`.
    - Why: Single query avoids N+1 (fetch all uploads, then count per upload)

- [ ] **GetUploadHistoryUseCase + API endpoint**
    - Effort: S
    - Dependencies: "Upload history repository method"
    - What: New `GetUploadHistoryUseCase` in `src/application/use_cases/get_upload_history.py`. `GetUploadHistoryCommand()` (empty). `GetUploadHistoryResult(entries: list[UploadHistoryEntry])`. Loads persons for name lookup, calls repo method, maps to result. New route: `GET /api/v1/uploads/history`. Response schema in `src/interface/api/schemas/uploads.py`. Run `pnpm --prefix web generate` for Orval hooks.
    - Why: Standard use case pattern, thin route handler

- [ ] **Upload history backend tests**
    - Effort: S
    - Dependencies: "GetUploadHistoryUseCase + API endpoint"
    - What: Integration test for repo method: create uploads with transactions, verify counts and date ranges. Use case unit test with mocked UoW. API integration test: create data, hit GET, verify response. Edge case: upload with zero transactions (possible after re-upload replaces all).
    - Why: Derived counts must match reality

#### Frontend

- [ ] **Upload history section on UploadPage**
    - Effort: M
    - Dependencies: "GetUploadHistoryUseCase + API endpoint"
    - What: New section below the upload form, always visible (not gated by step). Uses Orval-generated `useGetUploadHistory()` hook. `Card` with "Upload History" heading, table above `md:`, card layout below. Each entry shows: person name (`PersonBadge`), filename, date (`formatDate`), transaction count, shared count, date range. Empty state via `PageEmpty`. Loading via `PageLoading`. Invalidates on successful upload (`queryClient.invalidateQueries`). Caps at 20 with "Show all" toggle.
    - Why: Answers "when did we last upload?" directly on the page where you upload

- [ ] **Upload history frontend tests**
    - Effort: S
    - Dependencies: "Upload history section on UploadPage"
    - What: History section renders with data. Empty state. History refreshes after successful upload. MSW handler for the history endpoint.
    - Why: New UI section needs coverage

### v0.8.3: CSV Validation & Error Quality
**Goal**: Catch problems early with specific, actionable error messages — before the file hits the server and all at once instead of one by one.
**Context**: Validation currently happens entirely server-side in `parse_monarch_csv()`. Errors are specific (missing columns, invalid amounts, invalid dates) but the user sees them only after a round-trip. The parser raises on the first bad row, forcing a "fix one, reupload, find the next" loop. And `decode("utf-8-sig")` has no error handling — non-UTF-8 files produce a 500.
**What this unlocks**: Instant error feedback on the cheapest mistakes, fewer wasted round-trips, and all row errors surfaced in one pass.

#### Frontend

- [ ] **Client-side file validation in FileDropZone**
    - Effort: S
    - Dependencies: v0.8.1 (FileDropZone)
    - What: Extend `FileDropZone` to validate before calling `onFile`: (1) extension is `.csv`, (2) file is not empty (`size === 0`), (3) file is not unreasonably large (>10MB via configurable `maxSizeBytes` prop). Inline error below the drop zone using `destructive-muted` styling. Error clears on new file drop. `onFile` only called for valid files.
    - Why: Empty files and wrong file types are the most common upload mistakes
    - Notes: Monthly Monarch CSVs are 10-50KB. The 10MB limit catches accidental drops (images, bank PDFs).

- [ ] **Client-side CSV header validation**
    - Effort: S
    - Dependencies: "Client-side file validation"
    - What: After file passes FileDropZone, read the first ~1KB with `FileReader.readAsText()` and parse the header row. Compare against required Monarch columns (Date, Merchant, Category, Account, Original Statement, Notes, Amount, Tags). If missing, show error immediately: "This CSV is missing columns: X, Y." Define columns as a shared constant in `web/src/lib/csv-validation.ts`.
    - Why: Wrong CSV format (e.g., bank CSV instead of Monarch export) is the second most common error. Instant feedback with specific missing columns named.
    - Notes: Reads only the first line. Handles UTF-8 BOM.

- [ ] **Structured error display component**
    - Effort: S
    - Dependencies: none
    - What: New `web/src/components/UploadError.tsx` replacing the current raw `error.message` display. For 422 validation errors, renders with context (merchant names highlighted, column names as a list). For generic errors, renders fallback message.
    - Why: Structured display with context helps the user find and fix the problem faster

- [ ] **Client-side validation tests**
    - Effort: S
    - Dependencies: all above frontend items
    - What: FileDropZone extended: empty file rejection, oversized file rejection. CSV header validation: missing columns detected, valid headers pass. UploadError component: validation error renders detail, generic error renders fallback.
    - Why: Validation regressions are invisible until a user hits them

#### Backend

- [ ] **Encoding detection with actionable error**
    - Effort: S
    - Dependencies: none
    - What: In `src/interface/api/routes/uploads.py`, wrap `csv_bytes.decode("utf-8-sig")` in try/except `UnicodeDecodeError`. Raise `ValidationError("This file doesn't appear to be UTF-8 encoded. Try re-exporting from Monarch.")` instead of an unguarded 500. Apply to both preview and upload endpoints.
    - Why: Non-UTF-8 CSVs are rare but produce confusing 500 errors

- [ ] **Row-level error collection**
    - Effort: S
    - Dependencies: none
    - What: Change `parse_monarch_csv()` in `src/domain/parsing/monarch_csv.py` from raising on the first bad row to collecting all row errors, then raising with a batch message: "3 rows had problems: Row 12 (Starbucks): invalid amount '12.3.4'; Row 45 (Amazon): invalid date '2026-13-01'." Cap at `MAX_ROW_ERRORS = 25`. Valid rows are not partially imported when errors exist (fail the whole batch).
    - Why: Collecting all errors in one pass saves the "fix one, find the next" loop
    - Notes: Function signature and return type don't change — still returns `list[Transaction]` on success, raises `ValidationError` on failure.

- [ ] **Backend validation tests**
    - Effort: S
    - Dependencies: "Encoding detection", "Row-level error collection"
    - What: Encoding: non-UTF-8 file raises `ValidationError` with actionable message. Row errors: CSV with multiple bad rows collects all errors. Error cap: >25 bad rows shows 25 + "and N more". No partial import when errors exist.
    - Why: Error handling edge cases need explicit coverage

**Context**: The confirmation screen is bare: three numbers (new, updated, skipped) and an "Upload Another CSV" button. Post-upload is a decision point in the solo prep workflow — "what do I do next?" The current page leaves the user to figure that out. Additionally, the multi-step flow (form → preview → review → confirmed) provides no visual indicator of where you are in the process.
**What this unlocks**: Reduced upload anxiety, clearer post-upload guidance, and a polished end-to-end experience.

## Design Rationale

**Why responsive first**: The existing backlog had drag-and-drop as v0.8.0. But the page layout is broken on mobile — `grid-cols-[1fr_16rem]` with zero breakpoints. Building drag-and-drop into a broken layout means either the drop zone doesn't work on mobile, or you're doing responsive work twice. Layout goes first; everything else builds into a working container.

**Why not bundle responsive into v0.9.0**: The v0.9.x backlog is "Responsive layout" for the entire app — sidebar-to-bottom-nav, transaction tables, budget stacking. That's a large app-shell change. The upload page is an isolated fix: it has its own unique layout problem (the two-column grid that no other page uses). Fixing it here means v0.9.0 can skip it and focus on the harder problems.

**Why validation is its own release**: Validation improvements touch both frontend (client-side checks) and backend (parser error collection, encoding handling). Mixing them with drag-and-drop or upload history would create a large release with two independent risk areas. Isolating them makes each release independently shippable and testable.

**Why five releases**: Each is independently shippable and valuable. v0.8.0-v0.8.1 are pure frontend (fast). v0.8.2 is full-stack but scoped. v0.8.3 is the quality improvement the couple will feel most. v0.8.4 is the polish that makes the flow feel complete.
